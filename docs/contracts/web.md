# Contract: web

Jinja2 + HTMX pages over the services. Imports services, core and `pairing` (the QR only). Decisions: 0008, 0038, 0039, 0054, 0058, 0100-0105, 0150-0153, 0183, 0210-0212, 0184, 0200-0203, 0256-0258.

## Public API
- `command_center.web.create_router(container=None, *, csrf_token=None) -> APIRouter`. Mount it at `/`. It is hidden from OpenAPI. Without `container` it uses `request.app.state.container`.
- Mount it only on an app that has the API's `TrustedHostMiddleware` (`api.factory`): the CSRF token sits in the page, and the Host check is what stops a DNS-rebinding page from reading it. The router does not check the Host itself.
- The page expects `/static/vendor/htmx.min.js`. The file is vendored at `web/static/vendor/htmx.min.js` (htmx 2.0.11, decision 0054) and `api.create_app` serves `web/static` at `/static`. Nothing else is loaded from outside.

## Routes
| Path | Method | What |
|---|---|---|
| `/?date=` | GET | Today: the summary card (always present, five states), agenda, weather strip, needs-attention |
| `/summary/settings?date=` | POST | Form `enabled` (`on` or `off`) and `provider`; stores them through `SummaryControl`; returns the card (`generating` when ready to generate). A different provider drops today's stored summary (decision 0115). 400 for an unknown provider or an `enabled` other than `on`/`off` (nothing is stored), 404 without a control |
| `/summary/generate?date=&refresh=` | POST | Generates (or, with `refresh=true`, regenerates) the day's summary; returns the card |
| `/week?date=` | GET | Seven Monday-based columns; day load = sum of urgency |
| `/month?date=` | GET | Grid heat by load (0-4 against the busiest day) and top deadlines (8, open, most urgent first) |
| `/history?date=` | GET | One day of history (default today): completed by you, completed at the source, disappeared from its source, with times, sources and notes; previous and next day links. 404 without an item service; a bad date is 422. A paired phone may read it like the other pages (decision 0153) |
| `/items/{id}/done?ctx=&day=&dated=` | POST, DELETE | Check off, and Undo; answers the row drawn again (`_item_row.html`), plus an out-of-band delete of the attention copy when the click was on another list (decision 0152). 404 unknown id, or no item service |
| `/items/{id}/notes?ctx=&day=&dated=` | PUT, DELETE | Form `text`; saves or removes the note; answers the row with the details panel open and "Note saved." or the model's fixed message (the typed text stays in the box). 404 unknown id, or no item service |
| `/items/{id}?ctx=&day=&dated=` | PATCH, DELETE | Form `title`, `due_date`, `due_time`, `label` edits your own task; DELETE removes it and its note and check-off. 409 `Only your own tasks can be changed or deleted` for a synced item, 404 unknown id |
| `/tasks` | POST | Form `title`, `due_date`, `due_time`, `label` makes a local task. Success answers 200 with `HX-Redirect: /?date=<due day>`; a bad form answers the New task panel again, open, with what was typed and one fixed message |
| `/settings` | GET | The setup checklist, then a card per registered source and integration. Loopback only: 404 for a phone (decision 0211) |
| `/settings/{source}/status` | GET | Status fragment, polled every 2 s while `syncing`; also re-renders the Connect button. Loopback only: 404 for a phone (decision 0211) |
| `/settings/{source}` | PUT | Form fields plus an optional `action` (decision 0102): `connect` (default) validates, stores and returns the card, with `syncing`, the sync running as a background task; `unverified` stores without validating; `test` validates the stored credentials and returns only the result line; `sync` starts a sync and returns the result line plus the status. Another `action` is 422. On `weather` two more actions, `search` and `fill`, never store anything (decision 0183) |
| `/settings/{source}` | DELETE | Disconnect; returns the card |
| `/ai/settings` | PUT | Form `kind`, `base_url`, `model`, `enabled` (`on` or absent). Validates (the address with `core/urlcheck.require_chat_base_url`, its fixed reason shown), then `ChatSettings.set_provider` and `set_enabled`; returns the AI settings card, with what was typed after a refusal (only a plain http(s) address with a host, no user, password, query, fragment or key-shaped path segment and at most 300 characters is put back, and only a model name of at most 100 characters that is not key-shaped (`model_name_looks_like_api_key`, decision 0270: a known key prefix or an unbroken run of 32 or more letters and digits; long hosted names with separators are fine); a key pasted into either field is refused, never stored and never shown again). Loopback only; DENIED for a phone (decision 0202) |
| `/ai/test` | POST | Sends one fixed prompt to the stored provider (`ChatService.test_connection`); returns the `#result-ai` line: "OK: the provider answered the test." or the fixed redacted error. Also while chat is off. Loopback only (decision 0201) |
| `/chat` | GET | The chat page; switches both opt-ins off first (a page load starts a conversation). Loopback only: 404 for a phone, and 404 when the process has no chat service (decision 0203) |
| `/chat/message` | POST | Form `message`, `conversation_id` (empty to start), and `shown_history` / `shown_notes` (`on` or `off`, hidden inputs in the context block that the message form includes with `hx-include`). When either is present they become `ChatShown` and the message is refused with 409 and the fixed text "Settings changed in another tab; reload the page" if the stored opt-ins differ (decision 0256); with neither present the stored opt-ins decide. Calls `ChatService.reply`; answers the two turns, plus out-of-band the hidden conversation id, an empty message box and the New chat button. Errors are JSON `detail` with the API's statuses (404 off or unknown conversation, 400 bad message, 409 unusable provider setting or opt-ins changed since the page showed them, 429 with `Retry-After`, 502 provider failure, including "did not answer in time" after 120 s) so the global error flash shows them |
| `/chat/context` | POST | Form `include_history`, `include_notes` (`on` or absent); stores both opt-ins; returns the "What the assistant can see" block, open (decision 0200) |
| `/chat/new` | POST | Switches both opt-ins off and returns a fresh panel (decision 0200) |
| `/pair` | GET | The pairing page (loopback Host only, else 404) |
| `/pair/code` | POST | Mints a one-time token and returns the QR (SVG) and the token; CSRF-protected, loopback only; says how to set `CC_ALLOWED_HOSTS` when no tailnet host is configured |

`date` is optional (default: `AgendaService.today()`); a bad date is 422. Unknown source is 404.

## Behaviour
- The Today summary card (`_summary.html`, section `#summary-card`, decision 0113) has states `off` (explains the opt-in and what is sent, Enable button when there is a control), `no_key` (Gemini chosen and the Gemini card has no key; links to `/settings#source-gemini`), `generating`, `ready` (text and a Regenerate button) and `error` (a fixed message by reason; provider text never shown). A page load never calls the provider (decision 0116): a summary already stored for the day is `ready` at once, otherwise the card is `generating` and its `hx-trigger="load"` posts `/summary/generate`, so the text arrives after the page. Generation happens once per day on first need; Regenerate is explicit. Disabled means no provider is called.
- Every row on Today, Week and Month prints a priority badge (`Row.priority`, decision 0114): the number always, colour from a CSS hue (green 1 to red 10) in light and dark; `–` when the item has no priority. The week column load and month heat still use urgency sums.
- Every non-GET needs header `X-CSRF-Token` equal to the process token, else 403 (checked first).
- Settings fields per source: canvas `base_url`, `token`*; apple_calendar `username`, `app_password`*; learningsuite `urls`*(textarea); gmail `client_json`*(textarea); weather `latitude`, `longitude`; gemini `api_key`*; chat `api_key`*. (* secret: password input or masked textarea.) Gemini is credential-only (`SourceForm.credential_only`): its card shows "Connected" once the key is set (never "syncing", never polled), asks "Delete the stored key…" and PUT does not queue a sync. Its card states the free-tier caveat, that email addresses and numbers are redacted before sending, and that saving a key does not turn summaries on (decisions 0004, 0058). The `chat` card ("Chat provider key", decision 0172) is credential-only the same way: one secret field and a how-to (hosted providers need a key, local ones such as Ollama need none, saving it neither turns chat on nor picks a provider, Gemini chat uses the Gemini key); it has no provider or model controls.
- `/pair` and `/pair/code` are for the local browser only: a remote Host (or a loopback Host with a proxy header) gets 401 from the auth middleware without a token and 404 from the route with one (decision 0057). The QR holds `{"v":1,"url":"https://<tailnet host>","token":...}`; the token is never in a URL. These responses are the only ones that carry a secret, and only the one-time token.
- Which fields are secret is decided once, in `services.credential_fields` (decision 0100); `web/sources.py` derives `Field.secret` from it. Non-secret fields (canvas `base_url`, apple_calendar `username`, weather `latitude`/`longitude`) are prefilled with the stored value (`SourceSettings.values`), and after a failed submit with what was typed. A secret input is never prefilled, and a blank secret keeps the stored one. No response contains a secret value: cards show `set` and, for secrets, the last 4.
- A failed Connect changes nothing that is stored (the service writes only after `validate` passes). After a failure the secret inputs carry `hx-preserve`, so the browser keeps what was typed without the server sending it back (decision 0104; not exercised in a real browser).
- "Save anyway (unverified)" is shown only when `ConnectResult.can_save_unverified` is true, which is only after a `TransientError` (network), never after a rejected credential. It stores the typed values and records an `error` state starting "Saved unverified:", shown as "Needs attention" (decision 0101).
- Each card with something stored has "Test connection" (`action=test`) and, for a source that syncs, "Sync now" (`action=sync`); the result is a redacted line under the buttons (`#result-<source>`). Both are refused with a short message while another action on the source runs, and "Test connection" says to connect first when nothing is stored.
- Each card has a collapsible how-to (`<details class="howto">`, no JavaScript) from `web/howto.py`: Canvas base URL and token, Apple app-specific password, LearningSuite link, Gmail OAuth client, weather coordinates, Gemini key. Menu paths vendors change say "may differ" (decision 0103).
- The top of `/settings` is a checklist (`web/checklist.py`, `services.setup_checklist`): per source `Not connected`, `Connected` or `Needs attention` and the age of the last sync ("3 min ago"; "last attempt" when it did not end ok). The age uses the clock given to `SettingsService` (decision 0105).
- Gmail's Connect shows "Waiting for Google sign-in…" and allows a 15 minute request; others 2 minutes. The button reads "Reconnect" when the state is `reconnect`.
- The weather strip footer is "Weather data by Open-Meteo.com" linking to https://open-meteo.com/, then "(CC BY 4.0)" linking the licence page and "Open-Meteo terms" linking https://open-meteo.com/en/terms; the weather card on `/settings` carries the same three links and credits GeoNames as text (decision 0184).
- City search (weather card only, `SourceForm.city_search`, decision 0183): a "Find a city" form above the credentials form, `hx-put` to `/settings/weather` with `action=search` and the typed text in field `city`, so the text is in the body and never in a URL or the access log. It lists up to five candidates (name, region, country, population) from `services.geocode`, picks none, and shows fixed text for no match, a query under 2 or over 100 characters (not sent), rate limited (with the wait), failure (the service's redacted message) and no geocoder (`Container.geocode is None`). None of them repeats the query. "Use these coordinates" sends `action=fill` with `latitude`, `longitude` and `label`; the answer replaces the two inputs (`hx-swap-oob`) and says "Nothing is saved until you press Connect". `fill` refuses a value that is not finite or is out of range. Neither action stores anything; a `city` sent with Connect is ignored like any non-field. Both are 422 for another source and, like every PUT here, CSRF-checked and refused to a phone.
- Item controls (decisions 0150 to 0153): a row of an event that is stored (not weather) has a "Done" button (Undo once it is checked off), a details panel with a note box, and "Why this priority" (`core.scoring.explain`, computed at render time with the agenda's clock; no API field). A local task's panel also has Edit task and Delete task. The reason is the tooltip of a wrapper around the badge, so the badge's own `title` (decision 0114) is unchanged. Row ids are `row-<ctx>-<item id>`; `ctx` in the query is `agenda`, `attention`, `week` or `deadline`. Undo is offered only for the user's own check-off. With no item service no control is drawn and the item routes and `/history` are 404.
- New task: a collapsible panel on Today, Week and Month (`_new_task.html`), prefilled with the shown day. The date and time are in the settings timezone (`web/task_form.py`; title 1 to 200, label at most 80 characters). Every error is a fixed message that does not repeat the input. A local task is never swept by a sync or a disconnect (decision 0120).
- Every web item write is loopback-only: a paired phone gets 404 from the auth middleware, like `/pair/code` (decisions 0060, 0126, 0153).
- Phone view (decision 0210): every template context has `loopback`, true only for a loopback Host with no proxy header (`web/loopback.is_loopback`, false when unclassified). When it is false, Today, Week, Month and History are read-only: no Done or Undo button, no details panel (note box, Edit task, Delete task, reason text), no New task panel. Rows, the priority badge, a "note" chip and a "done" chip stay. Still drawn for a phone, and not usable by it: the nav links to Settings and Pair phone, and the summary card's controls.
- `/settings`, `/settings/{source}/status` and `/pair*` share one check, `require_loopback` (`web/loopback.py`): 404 "Not found" for a tailnet Host, a loopback Host with a proxy header, or an unclassified request. Their rows in the route policy are HIDDEN: the policy lets the request through and the page answers (decisions 0057, 0106, 0211).
- Failed htmx requests (decision 0212): htmx does not swap a 4xx or 5xx reply, so `base.html` inlines one `htmx:responseError` listener (`templates/_htmx_errors.js`). It shows the reply's JSON `detail` (the 409 "Only your own tasks can be changed or deleted", the 404 "No such item", the 403 "CSRF token missing or wrong") in the nearest `.flash` of the row (`li`), card or panel, and opens the `<details>` around it; any other reply shows "The server refused the request (<status>)." Text is set as text, never HTML. The failing reply is not swapped into the page.

- Chat page and AI card (decisions 0200 to 0203, 0256 to 0258): `/chat` shows the provider and model in use (never the address), a "What the assistant can see" disclosure with the exact `context_preview` text (works while chat is off), two default-off checkboxes (history, notes; stored settings that opening `/chat` and "New chat" switch off, so each conversation starts with neither), the transcript, a message box and "New chat". The conversation id lives in a hidden input. "New chat" is `hx-delete` to `DELETE /v1/chat/{id}` (it drops the form `Content-Type` htmx adds, which the API refuses for a write), then posts `/chat/new`. The `Chat` nav link is drawn only when `loopback` is true. The AI card on `/settings` (`web/ai_settings.py`, `_ai_card.html`) has provider, server address, model, a "Turn chat on" box and "Test connection", with a collapsible how-to per provider (Ollama, LM Studio or llama.cpp, Gemini; `web/howto.AI_HOWTOS`). The key is not on it: it stays on the write-only "Chat provider key" card. The chat and AI-card requests have an htmx timeout of 135 s, a little over the server's 120 s deadline, so the server's fixed error arrives before the browser gives up. The preview text can still go stale between page load and send (an agenda item changed meanwhile); only the two opt-ins are compared. None of this is exercised in a real browser; no test runs JavaScript.

## Past gap, fixed
Changing one field of a multi-field source (or Reconnect with nothing typed) used to hand the adapter a partial credential set. `SettingsService.connect` now merges the stored values under the submitted ones before `validate` (decision 0052; `docs/contracts/services.md`).
