# Contract: api

REST under `/v1`, bound to 127.0.0.1. `docs/generated/openapi.json` (and `api-reference.md`) hold every route, parameter and schema and are the machine contract for the separate mobile repo; this file holds behaviour and reasons only.

## Behaviour
- `create_app(container, *, sync_interval_minutes=None, remote_hosts=())` (`api/factory.py`) takes a `Container` or a factory called at startup (decision 0021). With an interval the lifespan runs a `SyncScheduler` (decision 0053). The production app is `command_center.app.create_app()`. The same app also serves the web pages at `/` (`web.create_router()`) and `web/static` at `/static`; the Host check below covers them too.
- Only the `Host` headers `localhost`, `127.0.0.1` (any port) and the names in `CC_ALLOWED_HOSTS` are served; anything else is 400 (`TrustedHostMiddleware` and `DeviceAuthMiddleware`). Reason: stops a web page on another origin from reaching the API through a rebinding hostname.
- Auth (`api/auth.py`, `install_auth`; decision 0057): the **Host header decides**. Tailscale Serve proxies to 127.0.0.1, so the socket address is always loopback, but the request carries the tailnet name. A loopback Host with no proxy header (`forwarded`, `x-forwarded-*`, `x-real-ip`, `via`, `tailscale-*`) is the local web UI and needs no token. Any other allowed Host, and a loopback Host that carries a proxy header, needs exactly one `Authorization: Bearer <access token>` on every route except `/v1/health`, `/v1/pair` and `/v1/pair/refresh`; otherwise 401 `{"detail": ...}` with `WWW-Authenticate: Bearer`, the same body for every cause. With no pairing service configured, remote requests are always refused.
- `POST /v1/pair` `{pairing_token, device_name?}` trades the one-time pairing token (128 bits, single use, 5 minutes) for `{device_id, token_type, access_token, access_expires_at, refresh_token}` (access token 15 minutes). `POST /v1/pair/refresh` `{refresh_token}` rotates: the old refresh credential stops working and presenting it again revokes the device. Five failures lock each of the two routes for 60 s (429 with `Retry-After`; the lock is global because every request arrives from 127.0.0.1). Every refusal is the same 401. Responses are `Cache-Control: no-store`; bodies reject unknown fields. 404 when pairing is not configured.
- `GET /v1/devices` lists paired devices (`id`, `name`, `created_at`, `last_seen_at`; never a token) and `DELETE /v1/devices/{id}` revokes one (204, or 404), which ends its access and refresh tokens at once. Both are bearer-secured in OpenAPI (`DeviceToken`); the other protected routers declare the same scheme so the mobile repo sees it.
- **A paired phone is scoped** (`api/policy.py`; decision 0060). A request that needs a token (a tailnet Host, or a loopback Host behind a proxy header) may read (GET, HEAD, OPTIONS) and call `POST /v1/sync`; every other write is refused after the token check, so a request with no token is still 401. `/v1` routes answer 403 `{"detail": "A paired phone may not do this"}` (`PUT`/`DELETE /v1/settings/{source}`, `DELETE /v1/devices/{id}`); the web UI's own writes answer 404. A new write route is refused for a phone until it is added to `REMOTE_WRITES` and to the table in `tests/test_remote_policy.py`. Loopback without a proxy header is unchanged.
- **Writes under `/v1` take JSON only** (decision 0060): a POST, PUT, PATCH or DELETE with any other Content-Type, two Content-Type headers, or a body and no Content-Type is 415 `{"detail": "Content-Type must be application/json"}`, for every caller. No body and no Content-Type is fine. `POST /v1/pair` and `/v1/pair/refresh` answer a *declared* form or `text/plain` type with 422 instead (they read a JSON model), and refuse the other two cases with 415 like any write. The web UI's forms are not under `/v1`.
- **Cross-site writes under `/v1` are 403** `{"detail": "Cross-site requests are not allowed"}` (decision 0060): `Sec-Fetch-Site: cross-site`, or an `Origin` that is not the request's Host. Browsers send these on a cross-origin `fetch` or form post; the phone app and curl send neither.
- Handlers parse, call one service method and return; logic lives in services.
- `GET /v1/health`: `{"status": "ok"}`. Liveness for the launcher and the phone.
- `GET /v1/events?from&to`: events overlapping `[from, to)`, scored now, ordered by time. Both bounds must carry a timezone; write `+` as `%2B` or use `Z`. `to` not after `from` is 422.
- `GET /v1/agenda/{day|week|month}?date=YYYY-MM-DD`: the day, Monday-based week or month containing `date`, in the configured timezone. `date` is required.
- `GET /v1/attention`: urgent items and owed or overdue email, most urgent first (see `services.md`).
- `GET /v1/settings`: per source (then per credential-only integration, today `gemini`; its `sync` is `null`, except an error state when the secret store is unavailable), per key `{set, last4}`, plus the last sync state (`syncing | ok | reconnect | error`). Write-only: no value is ever returned. The sync state's `message` is redacted (email addresses and digit runs of 6+ digits replaced) and at most 200 characters (decision 0052).
- `PUT /v1/settings/{source}` with `{"credentials": {key: value}}`: the body is merged over the stored credentials, so a key left out, blank or whitespace-only keeps its stored value (send only what changed; to clear a key, `DELETE` and connect again), and the adapter validates the merged set (decision 0052). The response `message` is redacted and at most 200 characters, like a sync message. It stores the result, then returns at once with `sync.status` `syncing`; the sync runs as a background task after the response and ends in `ok | reconnect | error`, visible in `GET /v1/settings` (decision 0025). In distributed mode the background task only queues a job for the source's worker, and `GET /v1/settings` shows what the normalizer recorded; the first state appears when the worker has reported (decision 0074). A rejected credential is **200 with `ok: false`** and nothing stored (decision 0020); the one exception is a secret store failure part-way through the writes, which reports `ok: false` and leaves the keys written so far. Unknown source is 404. For an integration (`gemini`, key `api_key`) the key is checked with one cheap Gemini call (15 s timeout), the response has `sync: null` and no sync follows (decision 0058).
- `DELETE /v1/settings/{source}`: removes every stored key, every stored event and the stored sync state of the source (decisions 0029, 0074), so its items leave the agenda. In distributed mode it also bumps the source's generation, so a sync already in flight for it is dropped when it reports: nothing of it comes back. Unknown source is 404.
- `POST /v1/sync`: syncs every source (never an integration such as `gemini`) and returns each `SyncState`; a failing source is a state, not an error. In distributed mode (decision 0074) nothing is fetched in the api: a job is queued for every connected source, each is returned as `syncing`, the others as last recorded (left out if never recorded), and the results appear in `GET /v1/settings` once the workers report. The response schema is the same.
- No response model has a field that can carry a credential, except the two pairing responses above, which carry the device's own new tokens once. A 422 (`ValidationErrorBody`, declared on every route that takes parameters) lists `loc`, `msg` and `type` only and never echoes the submitted input (decision 0023). A secret store failure appears as the error state `secret store unavailable`, never a 500 with detail.
- `GET /v1/summary?date=YYYY-MM-DD` (router `api/summary_routes.router`, always mounted; decision 0053): `{"summary": {headline, priorities, heads_up}, "provider", "cached"}`. 404 `Summaries are off` while `container.summary` is `None` (the default). A provider failure is still 200 with `provider` `stored` (an earlier day's summary) or `template`; see `services.md`. `date` is required. Decision: 0037.
- Events carry `raw`, which adapters must fill with public item fields only.
