# Contract: api

REST under `/v1`, bound to 127.0.0.1. `docs/generated/openapi.json` (and `api-reference.md`) hold every route, parameter and schema and are the machine contract for the separate mobile repo; this file holds behaviour and reasons only.

## Behaviour
- `create_app(container, *, sync_interval_minutes=None, remote_hosts=())` (`api/factory.py`) takes a `Container` or a factory called at startup (decision 0021). With an interval the lifespan runs a `SyncScheduler` (decision 0053). The production app is `command_center.app.create_app()`. The same app also serves the web pages at `/` (`web.create_router()`) and `web/static` at `/static`; the Host check below covers them too.
- Only the `Host` headers `localhost`, `127.0.0.1` (any port) and the names in `CC_ALLOWED_HOSTS` are served; anything else is 400 (`TrustedHostMiddleware` and `DeviceAuthMiddleware`). Reason: stops a web page on another origin from reaching the API through a rebinding hostname.
- Auth (`api/auth.py`, `install_auth`; decision 0057): the **Host header decides**. Tailscale Serve proxies to 127.0.0.1, so the socket address is always loopback, but the request carries the tailnet name. A loopback Host with no proxy header (`forwarded`, `x-forwarded-*`, `x-real-ip`, `via`, `tailscale-*`) is the local web UI and needs no token. Any other allowed Host, and a loopback Host that carries a proxy header, needs exactly one `Authorization: Bearer <access token>` on every route except `/v1/health`, `/v1/pair` and `/v1/pair/refresh`; otherwise 401 `{"detail": ...}` with `WWW-Authenticate: Bearer`, the same body for every cause. With no pairing service configured, remote requests are always refused.
- `POST /v1/pair` `{pairing_token, device_name?}` trades the one-time pairing token (128 bits, single use, 5 minutes) for `{device_id, token_type, access_token, access_expires_at, refresh_token}` (access token 15 minutes). `POST /v1/pair/refresh` `{refresh_token}` rotates: the old refresh credential stops working and presenting it again revokes the device. Five failures lock each of the two routes for 60 s (429 with `Retry-After`; the lock is global because every request arrives from 127.0.0.1). Every refusal is the same 401. Responses are `Cache-Control: no-store`; bodies reject unknown fields. 404 when pairing is not configured.
- `GET /v1/devices` lists paired devices (`id`, `name`, `created_at`, `last_seen_at`; never a token) and `DELETE /v1/devices/{id}` revokes one (204, or 404), which ends its access and refresh tokens at once. Both are bearer-secured in OpenAPI (`DeviceToken`); the other protected routers declare the same scheme so the mobile repo sees it.
- **A paired phone is scoped** (`api/policy.py`; decision 0060). A request that needs a token (a tailnet Host, or a loopback Host behind a proxy header) may read (GET, HEAD, OPTIONS) and call `POST /v1/sync`; every other write is refused after the token check, so a request with no token is still 401. `/v1` routes answer 403 `{"detail": "A paired phone may not do this"}` (`PUT`/`DELETE /v1/settings/{source}`, `DELETE /v1/devices/{id}`, and every item write: decision 0126); the web UI's own writes answer 404. A new write route is refused for a phone until it is added to `REMOTE_WRITES` and to the table in `tests/test_remote_policy.py`. A GET a phone may not make is listed in `REMOTE_DENIED_READS` (today `/v1/geocode`; decision 0182) and answers 403 the same way. Loopback without a proxy header is unchanged.
- **Writes under `/v1` take JSON only** (decision 0060): a POST, PUT, PATCH or DELETE with any other Content-Type, two Content-Type headers, or a body and no Content-Type is 415 `{"detail": "Content-Type must be application/json"}`, for every caller. No body and no Content-Type is fine. `POST /v1/pair` and `/v1/pair/refresh` answer a *declared* form or `text/plain` type with 422 instead (they read a JSON model), and refuse the other two cases with 415 like any write. The web UI's forms are not under `/v1`.
- **Cross-site writes under `/v1` are 403** `{"detail": "Cross-site requests are not allowed"}` (decision 0060): `Sec-Fetch-Site: cross-site`, or an `Origin` that is not the request's Host. Browsers send these on a cross-origin `fetch` or form post; the phone app and curl send neither.
- Handlers parse, call one service method and return; logic lives in services.
- `GET /v1/health`: `{"status": "ok"}`. Liveness for the launcher and the phone.
- `GET /v1/events?from&to`: events overlapping `[from, to)`, scored now, ordered by time. Both bounds must carry a timezone; write `+` as `%2B` or use `Z`. `to` not after `from` is 422.
- `GET /v1/agenda/{day|week|month}?date=YYYY-MM-DD`: the day, Monday-based week or month containing `date`, in the configured timezone. `date` is required.
- `GET /v1/attention`: urgent items and owed or overdue email, most urgent first (see `services.md`).
- `GET /v1/settings`: per source (then per credential-only integration, today `gemini`; its `sync` is `null`, except an error state when the secret store is unavailable), per key `{set, last4}`, `values` (an object of the stored value of each set non-secret key: canvas `base_url`, apple_calendar `username`, weather `latitude`/`longitude`; empty for the rest; decision 0100, additive; **empty for every request that is not loopback**, so a paired phone never receives it, decision 0106), plus the last sync state (`syncing | ok | reconnect | error`). Write-only for secrets: no secret value is ever returned. `DELETE /v1/settings/{source}` strips `values` the same way. The sync state's `message` is redacted (email addresses and digit runs of 6+ digits replaced) and at most 200 characters (decision 0052).
- `PUT /v1/settings/{source}` with `{"credentials": {key: value}}`: the body is merged over the stored credentials, so a key left out, blank or whitespace-only keeps its stored value (send only what changed; to clear a key, `DELETE` and connect again), and the adapter validates the merged set (decision 0052). The response `message` is redacted and at most 200 characters, like a sync message. It stores the result, then returns at once with `sync.status` `syncing`; the sync runs as a background task after the response and ends in `ok | reconnect | error`, visible in `GET /v1/settings` (decision 0025). In distributed mode the background task only queues a job for the source's worker, and `GET /v1/settings` shows what the normalizer recorded; the first state appears when the worker has reported (decision 0074). A rejected credential is **200 with `ok: false`** and nothing stored (decision 0020), and `can_save_unverified` (additive, default false) is true only when the check failed on the network, not on a rejection. the one exception is a secret store failure part-way through the writes, which reports `ok: false` and leaves the keys written so far. Unknown source is 404. For an integration (`gemini`, key `api_key`) the key is checked with one cheap Gemini call (15 s timeout), the response has `sync: null` and no sync follows (decision 0058). Send `"unverified": true` (additive, default false) to store the credentials without checking them: the response is `ok: true` with an `error` `sync` whose message starts `Saved unverified:`, no sync is queued, and nothing is stored when no value is sent. Only a client that saw `can_save_unverified` should send it; the server does not check why (decision 0101). `GET /v1/settings` shows that state except in distributed mode, where it is in the response only.
- `DELETE /v1/settings/{source}`: removes every stored key, every stored event, the stored sync state and the item history and notes of the source (decisions 0029, 0074, 0127), so its items leave the agenda. In distributed mode it also bumps the source's generation, so a sync already in flight for it is dropped when it reports: nothing of it comes back. Unknown source is 404. The order is cancel (the generation bump), then keys, then a second bump, then events and state (decisions 0085, 0086); the response shape is unchanged. A failure is a 200 with the same `SourceSettings` shape and an `error` `sync`, never a 5xx: if the bump fails nothing was deleted, `keys` still lists what is stored and `sync.message` is `Could not disconnect; nothing was removed. Try again`; if the delete of events and state fails the credentials are already gone, `keys` is empty and `sync.message` says the disconnect is incomplete and to disconnect again, which finishes it. If the secret store is unavailable the result is `keys: {}` with `sync.message` `secret store unavailable` and nothing is purged, although the keys may still be stored. A successful disconnect has `sync: null`.
- `POST /v1/sync`: syncs every source (never an integration such as `gemini`) and returns each `SyncState`; a failing source is a state, not an error. In distributed mode (decision 0074) nothing is fetched in the api: a job is queued for every connected source, each is returned as `syncing`, a connected source whose job could not be queued (Redis down) as an `error` state (`Could not queue the sync; it will be retried at the next scheduled round`), the others still being queued (decision 0085), the rest as last recorded (left out if never recorded), and the results appear in `GET /v1/settings` once the workers report. The response schema is the same.
- No response model has a field that can carry a credential, except the two pairing responses above, which carry the device's own new tokens once. A 422 (`ValidationErrorBody`, declared on every route that takes parameters) lists `loc`, `msg` and `type` only and never echoes the submitted input (decision 0023). A secret store failure appears as the error state `secret store unavailable`, never a 500 with detail.
- `GET /v1/summary?date=YYYY-MM-DD` (router `api/summary_routes.router`, always mounted; decision 0053): `{"summary": {headline, priorities, heads_up}, "provider", "cached"}`. 404 `Summaries are off` while `container.summary_service()` is `None` (the default; with a `SummaryControl` that follows the stored switch, decision 0112). A provider failure is still 200 with `provider` `stored` (an earlier day's summary) or `template`; see `services.md`. `date` is required. Decision: 0037.
- `GET /v1/geocode?q=` (router `api/geocode_routes.router`; decisions 0180-0182): up to 5 candidates `{name, region, country, latitude, longitude, population}` in Open-Meteo's order, `[]` when nothing matches; it never picks one. `q` is trimmed, 2 to 100 characters (else 422, never echoing it). **Loopback only**: a paired phone is 403. At most 10 searches per 60 s for everyone (429 with `Retry-After`; a failed search counts). A provider failure is 502 with `detail` `City search failed: ...`, redacted and at most 200 characters; 404 when no geocoder is wired. Responses are `no-store`. The query text is never logged (not by the service, httpx or uvicorn's access log).
- **Items, check-off, notes and history** (router `api/items.py`, always mounted; 404 `Items are not enabled` while `container.items` is `None`; decisions 0120-0127):
  - `POST /v1/items/{id}/done` marks an item done by you (`completed_by` `user`) and returns the item as the agenda shows it (`status` `done`, `urgency` 0, `priority` null); `DELETE` undoes it. Both are idempotent: checking off twice keeps the first time, and undoing leaves an item the source reports done as done. An unknown id is 404 `No such item`.
  - `PUT /v1/items/{id}/notes` `{"text"}` sets the note (1 to 4000 characters of plain text, blank is refused, a new `PUT` replaces the old note); `DELETE` removes it and is harmless when there is none. The response is the item, with `has_note`. A bad note is 422 `note must be 1 to 4000 characters` and the text is never echoed or logged, and never sent to a summary provider (decision 0125). Every event carries `has_note` (additive, default false); the note text only comes back through `GET /v1/history`.
  - `POST /v1/items` creates a local task (kind `task`, source `local`), `PATCH`/`DELETE /v1/items/{id}` change or delete one; only local tasks can be changed or deleted (others are 409). No sync ever prunes a local task.
  - `GET /v1/history?from=YYYY-MM-DD&to=YYYY-MM-DD` (both required, inclusive, in the settings timezone, at most 366 days; `to` before `from` or a longer range is 422): a list of days, oldest first, that have anything, each `{day, done_by_you, done_by_source, gone}`. An entry is `{item_id, source, kind, title, at, group, note, link, completed_by, reopened}` (`group` is the list it is in; `note` and `link` may be null; the same `item_id` can appear in several entries): `completed_by` is `user`, `source`, or null for an item that disappeared from its source (removed, not done, decision 0122). Every completion is its own entry on its own day (decision 0131): a source completion is appended on each open-to-done change a sync sees, so an item the source completes twice appears twice, and an item you checked off and the source also completed appears once under `done_by_you` and once under `done_by_source`. History is permanent: if the source later reports the item open again, its entries stay with `reopened: true` on the source entries completed before that reopen (false otherwise, and always false for your own check-off), while the agenda shows the item open. Undoing a check-off removes that one `done_by_you` entry (it corrects a mistake) and nothing else. An item is done in the agenda when you have checked it off or the source currently reports it done. `gone` means the item stopped being returned by its source inside the sync window: a deleted item, and also one rescheduled past the end of the window, until it returns. Days are local days, so a 23 or 25 hour day holds exactly its own entries (decision 0123).
  - The Mac's web pages use the same item service through their own routes (`/items/...`, `/tasks`, `/history`; `docs/contracts/web.md`, decisions 0150-0153). They add nothing to `/v1`: the "Why this priority" reason is computed in the web layer and is not an API field.
  - **Disconnecting a source deletes its history and notes** along with its events (decision 0127); local tasks and other sources keep theirs.
  - The write routes are loopback-only: a paired phone gets 403 on all of them (decision 0126). `GET /v1/history` is a read and is open to a phone, notes included.
- Events carry `raw`, which adapters must fill with public item fields only.
- Every event in `/v1/events`, `/v1/agenda/{period}` and `/v1/attention` carries `priority`: an integer 1-10 (`ceil(urgency / 10)`) or `null` for a done or ended item (decision 0110). It is computed from `urgency`, additive for the mobile repo, and never stored.

- `GET /v1/tasks` (router `api/tasks.py`, always mounted; decisions 0332, 0370, 0371): tasks, assignments and email in the sync horizon, plus open tasks and assignments with no due time (at most 200, newest first by `fetched_at` then id; done undated items are left out; decision 0372), as `{id, title, source, due, link, done, priority, reasons[{code, points, text}]}`, sorted by `priority` descending then `due` ascending (none last). Read-only, so a paired phone may call it; no write routes. Done dated items stay with `done` true. An undated open item has the 0-point reason `no_due` ("No due date"); a plain manual one scores 1. Reasons carry no email body or secret.
- `GET /v1/needs-me` (router `api/needs_me.py`, always mounted; decisions 0385, 0386): at most 20 items that need attention across tasks, assignments, email and events, as `{id, title, kind, source, at, link, priority, reasons[{code, points, text}]}` (`at` is the due time, else the start; `link` is the source's own link or null), sorted by `priority` descending, then `at` ascending, then id. Read-only, so a paired phone may call it; no write routes. Done and checked-off items are left out; there is no dismiss yet. `/v1/attention` is unchanged.

- **Dashboards and display settings** (router `api/dashboards.py`, always mounted; 404 `Dashboards are not enabled` while `container.dashboards` is `None`; decisions 0355 to 0358): `GET`/`POST /v1/dashboards`, `PUT /v1/dashboards/order`, `GET`/`PUT`/`DELETE /v1/dashboards/{item_id}` (the id; the parameter name is explained in 0357), `GET`/`PUT /v1/display-settings`. The layout is the UI's version 1 document, validated with fixed limits (0355). A replace, a delete and a display save need `If-Match: "<revision>"`: missing 428, malformed 400, stale 409; the revision is also the response `ETag`. Reads are open to a paired phone; every write is loopback-only (403 for a phone) and keeps the JSON-only and cross-site rules. Display settings hold no AI provider setting and no secret.

## Chat
Loopback only for a paired phone (403; decision 0165). Every response has `Cache-Control: no-store`.
- `POST /v1/chat` `{message (1 to 2000 characters), conversation_id?}` -> `{reply, conversation_id}`. 404 chat is off or the conversation is unknown, 409 not configured or the provider address is refused, 429 rate limited (10 per minute; `Retry-After`), 502 the provider failed (including a reply over 1 MiB, a stored key that may not be sent over plain http to a non-loopback address, and any exception the provider's SDK raises that is not otherwise recognised: that last one is always the text `The chat provider failed: the request could not be completed`, never a 500). Error text is fixed and redacted (decisions 0220, 0222, 0223).
- `GET /v1/chat/context-preview` -> `{enabled, include_history, include_notes, context}`: exactly the redacted context a message would carry. Works while chat is off. 409 when the provider setting is unusable.
- `DELETE /v1/chat/{conversation_id}` -> 204, also while chat is off; 404 unknown; 422 for an id that is not 1 to 64 letters, digits, `_` or `-`.
Read the generated reference for fields. Decisions 0160-0169.
