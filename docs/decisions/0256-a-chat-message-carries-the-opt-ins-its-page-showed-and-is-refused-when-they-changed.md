# 0256. A chat message carries the opt-ins its page showed and is refused when they changed

Status: accepted; amends 0200 (the page still shows the stored opt-ins, but a send now checks them)

Context: Decision 0200 made the history and notes opt-ins stored settings shared by every tab, and switched both off whenever `/chat` opens or "New chat" is pressed. That left a stale page able to disclose more than it showed: tab A opens `/chat` (both reset, both unticked), tab B ticks history, tab A sends, and the prompt holds "History" although tab A showed it unticked. 0200 rejected "opt-ins kept only in the page and sent with each message" because the API has no such field and a hidden page state could differ from the stored one.
Decision: The context block holds two hidden inputs, `shown_history` and `shown_notes` (`on` or `off`), set to what the page rendered; the message form includes that block with `hx-include`. `POST /chat/message` turns them into a `ChatShown` and passes it to `ChatService.reply(..., shown=)`. The service compares it with the stored opt-ins on the very config read that builds the context, once before the rate limit (a refusal uses up no message) and again after the lock is acquired (a tick made while the message waited is caught). On a difference it raises `ChatSettingsChangedError`, the page answers 409 with the fixed text "Settings changed in another tab; reload the page", and nothing reaches the provider. The stored settings stay the single source of truth; the hidden values are only a claim the service checks. One value alone counts the other as off; neither present (the API, an old page) keeps the stored-setting meaning of 0200.
Alternative: Keep the opt-ins in the page only (rejected again: the preview and the stored setting would then disagree). Re-render the opt-ins on a timer or with a server push so a stale page corrects itself (rejected: still a window, and it needs JavaScript that no test runs). Send whatever is stored and show a note afterwards (rejected: the disclosure comes after the send).
Reason: The page's promise is "what you see is what is sent". A cheap equality check on the same read makes the promise hold even across tabs, and fails closed: when in doubt nothing is sent.
Consequences: A user with two tabs open sees one refusal and must reload; reloading resets both opt-ins (0200), so the second tab starts clean. The preview text itself can still go stale between page load and send (an agenda item changed meanwhile); only the two opt-ins are compared.
Where: `services/chat.py` (`ChatShown`, `_require_shown`), `services/errors.py` (`ChatSettingsChangedError`), `web/chat_page.py` (`/chat/message`), `templates/_chat_context.html`, `templates/_chat_panel.html`; `tests/test_chat_shown_optins.py` (the two-client case), `docs/contracts/services.md`, `docs/contracts/web.md`.
Revisit when: The opt-ins move into the conversation (the revisit trigger of 0200), or the context preview is compared too.
