# 0101. An unverified save is an `error` sync state whose message starts "Saved unverified:", offered only after a TransientError

Status: accepted

Context: Task A1 adds "Save anyway (unverified)", for a connect that failed because the network was down, and says the typed values are stored "with a sync state saying unverified". `SyncStatus` is a closed Literal in `core/sync_state.py` (`syncing | ok | reconnect | error`), also published in `openapi.json`.
Decision: `SettingsService.save_unverified(source, creds)` stores the typed values over the stored ones (blank keeps, as in `connect`) without calling `validate`, and records an `error` state with the fixed message `UNVERIFIED_MESSAGE`, which starts with `UNVERIFIED_PREFIX` ("Saved unverified:"). No sync is queued. The page shows that state as "Needs attention". `connect` sets the new `ConnectResult.can_save_unverified` (default false) only when `validate` raised `TransientError`; a rejected credential (`AuthExpired`), a `FatalError` and a validation result with `ok` false never set it. The API accepts the same through an optional `unverified` flag on `PUT /v1/settings/{source}`. In distributed mode `record_error` does not store the state (decision 0074), so there the unverified message is in the response only and a later page load shows the source as connected until a worker reports.
Alternative: A new `unverified` member of `SyncStatus` (a core change that other sessions are editing, and an enum change in the mobile contract); or leave the offer to the page with no service flag (the page cannot tell a network failure from a rejection).
Reason: A prefix on an existing status needs no core or enum change, and "error" already means "needs attention" everywhere. The two new fields are additive. Restricting the offer to `TransientError` is what the card asks for: nothing is gained by saving a password the server said is wrong.
Where: `UNVERIFIED_PREFIX`, `UNVERIFIED_MESSAGE`, `SettingsService.save_unverified`, `_check` in `src/command_center/services/settings.py`; `ConnectResult.can_save_unverified` in `services/models.py`; `ConnectRequest.unverified` in `api/settings.py`; the label in `web/cards.py`. A request that sends `unverified` (the API flag or the form `action`) is saved whatever the earlier result was, even for credentials the adapter rejected, and an empty submission is refused with `NOTHING_TO_SAVE_MESSAGE`. A forged request with `action=unverified` after an auth failure would be saved too: the offer is a UI rule, not a server check, because the service cannot know why the client skipped the check.
Revisit when: Core can take a real `unverified` status (supersede this record), or distributed mode needs the state to survive a reload.
