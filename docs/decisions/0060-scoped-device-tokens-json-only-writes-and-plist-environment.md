# 0060. Scoped device tokens, JSON-only and same-site API writes, and an environment block in the LaunchAgent

Status: accepted

Context: Task 3d (security-critical). Decision 0057, item 12 (c) accepted that a paired phone is trusted like the web UI: any `/v1` route and the settings pages, including connecting or deleting sources, creating a pairing code and revoking other devices. Item 9 left the older `/v1` writes without any CSRF defence beyond the Host check. Item 12 (b) left the LaunchAgent without `CC_ALLOWED_HOSTS` and `CC_PORT`.
Decisions:
1. **A phone is read-only plus `POST /v1/sync`.** "A phone" is any request `core.hosts` classifies as REMOTE (a listed tailnet Host, or a loopback Host that carries a proxy header) after it has presented a valid token. `api/policy.remote_may_call(method, path)` allows GET, HEAD and OPTIONS, and the exact pair `POST /v1/sync`; nothing else. It is a default deny on the method, so a new write route is refused for a phone until someone adds it to `REMOTE_WRITES`. Loopback requests without proxy headers are not touched. `/v1/health`, `/v1/pair` and `/v1/pair/refresh` stay open and unscoped (they are how a phone gets a token). A websocket from a phone is closed with 1008: no route in its scope uses one.
2. **Order of refusals** in `DeviceAuthMiddleware`: 400 unknown Host, 401 no valid token, 403/404 outside the phone's scope, 403 cross-site write (item 6), 415 wrong content type, then the route. A caller with no token never learns which routes exist.
3. **Status of a refusal.** `/v1` routes answer 403 `{"detail": "A paired phone may not do this"}`. The web UI's own routes (`/settings/{source}` PUT and DELETE, `POST /pair/code`) answer 404 `{"detail": "Not Found"}`, because `tests/test_web_pair.py` already requires a phone's `POST /pair/code` to be 404 and the card could not touch that test. The card asked for 403 on creating a pairing token; that one route is 404 instead. Either way no handler runs and nothing is minted.
4. **`GET /v1/devices` stays readable by a phone.** The card lists `/v1/devices*` among the refused routes, but `tests/test_pair_api.py::test_devices_needs_a_token_from_the_tailnet` asserts a paired phone gets 200 from it, and the card says tests are new-only. The list carries id, name and timestamps, never a token. `DELETE /v1/devices/{id}` is refused (403), which is the part that matters: a phone cannot revoke another device or itself. To refuse the read too, add `/v1/devices` to a denied prefix in `api/policy.py` and change that one test.
5. **JSON-only writes under `/v1/`.** A POST, PUT, PATCH or DELETE whose Content-Type is not exactly one `application/json` (any case, parameters allowed) is 415 `{"detail": "Content-Type must be application/json"}`. Two header cases are refused as well: two Content-Type headers, and a body (Content-Length other than 0, or Transfer-Encoding) with no Content-Type, because FastAPI parses a typeless body as JSON and a cross-site `fetch` with a typeless Blob sends exactly that without a preflight. A request with no body and no Content-Type passes: the phone's `POST /v1/sync` and the DELETEs send neither. This applies to loopback callers too, since the browser on the Mac is the CSRF target. The web UI's form posts are outside `/v1/` and keep their `X-CSRF-Token`. `POST /v1/pair` and `POST /v1/pair/refresh` are exempt from one part only: a *declared* form or `text/plain` type still reaches their JSON body model and is 422, because `tests/test_pair_api.py` asserts 422. They still get 415 for a typeless body and for two Content-Type headers (a typeless body would otherwise reach the handler and spend a failure of the global limiter, which a page could use to lock the real phone out of refresh). The card says "every write route"; the declared-type case is the exception, with the reason here and in `tests/test_json_only_writes.py`.
6. **Cross-site writes are refused.** A bodiless `fetch(url, {method: "POST", mode: "no-cors"})` from a page in the Mac's browser needs no preflight and carries no Content-Type, so the JSON rule alone would let it start `POST /v1/sync` (the reviewer found this; a sync spends upstream calls and quota). A write under `/v1` whose `Sec-Fetch-Site` is `cross-site`, or whose `Origin` is present and is not the request's own Host (`null` included), is 403 `{"detail": "Cross-site requests are not allowed"}`, for every caller, before the content-type check. The phone app and curl send neither header, so they are unaffected; the web UI's own origin matches its Host. This is a refusal on header evidence, not a CSRF token: a client that sends neither header is not stopped, which only matters for a non-browser, and a non-browser attacker has no access to the loopback port. Impact if a browser omitted both headers: a sync, no data change.
7. **Route classification is a test.** `tests/test_remote_policy.py` walks the app's real routes (FastAPI 0.16x nests included routers, so `tests/route_support.py` descends them) and compares them with a table in both directions: a route missing from the table fails, and so does a table entry with no route. A route a phone may not call is requested with a real token and must be refused with the handler unrun (a device named in the URL is still there, no pairing token minted, nothing stored). The walker fails on a route with no methods (a websocket) and drops HEAD only beside GET and never drops OPTIONS, so an explicit HEAD or OPTIONS handler cannot dodge the table.
8. **LaunchAgent environment.** `launch_agent.build_plist(program, log_dir, environment=None)` writes an `EnvironmentVariables` block only for `ENVIRONMENT_KEYS = ("CC_ALLOWED_HOSTS", "CC_PORT")`; any other key is a `ValueError` naming the key (never its value), so the generator cannot be handed a secret. `launch_environment(os.environ)` picks those two, skipping unset or blank ones, and `desktop/main.py` passes it at install time. Both are non-secret settings. The value is a snapshot: change the variables, toggle **Launch at login** off and on to refresh the plist. The default (no environment) keeps the old output byte for byte.
9. **API contract for the mobile repo.** No route, parameter or schema changed: `gen:build` leaves `docs/generated/` identical. What changed is behaviour for a paired phone, which is a restriction (403/404/415), so it is recorded here and in `docs/contracts/api.md` and `docs/mobile.md` for the mobile repo. The new refusals are not in `openapi.json` because they come from middleware, like the 401.
Alternative: (a) Refuse `GET /v1/devices` as the card words it (needs an edit to an existing test). (b) 403 for the web routes too (needs edits to two existing tests in `test_web_pair.py`). (c) A per-route dependency or decorator marking each route's scope, so the scope sits beside the handler (a forgotten decorator would fail open; a method-based default fails closed, and the test catches a missing classification either way). (d) Exempt nothing from JSON-only and change the two `test_pair_api.py` tests from 422 to 415. (f) Accept the bodiless cross-site POST and say so (it only costs a sync); rejected because the fix is a few lines and the sync is not free. (g) Require a custom header (for example `X-Requested-With`) on every `/v1` write: it would break the phone app and every existing client. (e) A scope claim inside the token (the phone has one scope; a second one is a schema change to the devices table).
Reason: a stolen phone or a compromised tailnet peer should be able to see the agenda and ask for a sync, not change which accounts are connected or sign other devices out; and a page open in the Mac's browser should not be able to reach a write with a form post, a text/plain body or a bodiless no-cors POST, whatever Host check it passes.
Where: `api/policy.py`, `api/auth.py`, `desktop/launch_agent.py`, `desktop/main.py`; tests `test_remote_policy.py`, `test_json_only_writes.py`, `test_cross_site_writes.py`, `test_desktop_launch_agent_environment.py`, support `route_support.py`.
Supersedes: item 12 (c) of 0057 ("a paired phone is trusted like the web UI") and, in part, item 12 (b) (the LaunchAgent environment; a non-secret settings file is still not built) and item 9 (older `/v1` writes now refuse non-JSON; there is still no CSRF token on them).
Revisit when: the phone needs another write (add it to `REMOTE_WRITES` with a test row); `GET /v1/devices` should be refused; the web UI's refusals should be 403; a second Host is allowed to be local; Tailscale identity headers are verified and scopes can differ per device.
