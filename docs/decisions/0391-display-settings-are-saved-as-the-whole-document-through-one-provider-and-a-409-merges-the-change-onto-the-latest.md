# 0391. Display settings are saved as the whole document through one provider, and a 409 merges the change onto the latest

Status: accepted

Context: Card E2. `GET` and `PUT /v1/display-settings` replace the whole document under a revision (0356, `If-Match`, 428/400/409; writes are loopback only, 0357). The UI had an in-memory `DisplayProvider` and `ThemeProvider` (0322, 0340) and a zoom slider kept in component state. The next card (app shell) needs `privacy_mode` from the same document and must not build a second writer.
Decision:
- `useDisplaySettings()` (`ui/src/features/display/display-settings.tsx`) returns the settings, an `update(patch)` function, the save status with one fixed sentence for it, and `loaded` and `available` flags. It reads a context set by `DisplaySettingsProvider`, which main.tsx mounts once inside the query client and the theme and display providers. The shell card calls `update({ privacy_mode })` on the same hook, unchanged. Outside a provider the hook returns the defaults with `available: false` and a no-op `update`, so components rendered in isolation (existing tests) still work.
- The provider owns one `DisplaySaver` (`display-saver.ts`), shaped like `LayoutSaver` (0362): a pause of 600 ms after the last change, one write at a time, a change made during a write is sent after it against the new revision. It keeps the last server document and the keys changed since, and writes server document plus those keys, so `privacy_mode`, `owed_replies_as_tasks` and `source_colors` always go back as read. `toDocument` copies exactly the server's ten keys and never `revision` or `updated_at` (the input is strict).
- On a 409 the saver reads the latest document (query cache bypassed), lays the same changed keys on it, writes once more and reports "merged" with a fixed notice. This is the "reload, notify and reapply" of the card, and differs from 0362 on purpose: a layout is one object whose conflict loses the user's edit, but a display change is a few independent keys, so keeping what the other writer changed and re-applying only what this user just touched loses nothing. A second conflict in a row, or any other failure (a paired phone is refused, the network is down, the first read failed), reports "error" with a fixed sentence ("Could not save display settings. They apply to this session only."), keeps the local value on screen, and keeps the changes queued for the next change. The server's text never reaches the page.
- Settings are applied to the root element by `applySettings` (attributes only, no inline style: 0301) and to the grid through the `zoom` value. The provider also pushes theme and the four display values into the in-memory providers, so the `/today` header's theme switcher shows the truth.
- `/today` keeps its header ThemeSwitcher (it is untouched by this card); on `/dashboard` the router hides it and the Display popover replaces it, together with the dashboard's zoom slider. A change made in the `/today` switcher is in memory only, as before. At cutover Today becomes the dashboard and the switcher goes.
- Values are clamped (`normalize`) before they are shown or sent: glow 0 to 1.6 in 0.1 steps, text size 90 to 150 in 5, zoom 70 to 130.
Alternative: A hook that owns its own saver per component (rejected: two components would write against stale revisions). Reuse `LayoutSaver` (rejected: it is typed on a layout and drops the change on a conflict). Drop the local change on a 409 as 0362 does (rejected, see above). Persist to `localStorage` (rejected: banned, rule 7). A PATCH route (rejected here: a new api decision, and 0389 already notes it).
Reason: One writer with one revision cannot lose a key it has no control for, and a shared provider lets any card read or change one key without another request pipeline.
Where: `ui/src/features/display/` (`display-api.ts`, `display-saver.ts`, `display-apply.ts`, `display-settings.tsx`); `ui/src/main.tsx`; `ui/src/router.tsx`; `ui/src/features/dashboard/dashboard-view.tsx`.
Revisit when: a third writer exists (a PATCH route), the app shell removes the `/today` switcher, or a failed write should offer a Retry button.
