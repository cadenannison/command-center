# 0120. The item ledger is a sparse table beside events, not a row per item

Status: accepted

Context: Task B1 asks for a ledger of items so that a completion, a removal and a note outlive the event row. The event rows are replaced on every sync, so anything the user or a source did to an item has to live somewhere a replace does not touch. A full ledger (a row for every item ever seen) would mirror the events table and double every sync write.
Decision: `item_ledger` is keyed by (user_id, item_id) and holds a row only when there is something to remember: a note, a user check-off, a completion seen at the source, or an item that vanished. It also keeps a snapshot (source, kind, title, anchor, link) so the history can show an item after its event is gone. A row that loses its last reason to exist (an undone check-off, a removed item that came back, a deleted note) is deleted. Local tasks (source `local`, kind `task`) are ordinary rows in the events table and are never pruned by a sync. The `ItemLedger` port in `core/ports.py` is the only way services reach it. `ItemLedger` marks (`ItemMark`) are overlaid on events by `core.ledger.overlay_marks`, which sets `has_note` and status `done` and recomputes the derived `priority` (None when done).
Alternative: A full ledger with a row per item and a state column (simpler queries, but every sync writes one row per item and the table grows with the whole calendar); storing note and done flags on the events table (a replace deletes and rewrites those rows, so the flags would need to be carried across every merge).
Reason: Most items never get a note or a check-off. A sparse table costs nothing for them, survives a replace by construction, and the rows that do exist are exactly the ones the history needs. This deviates from the card's wording ("a ledger of items"); the project manager should confirm.
Where: `src/command_center/storage/sqlite_ledger.py` (table, `record_sync`), `sqlite_items.py` (`SqliteItemLedger`), `core/ledger.py`, `core/ports.py` (`ItemLedger`), `services/items.py`, `services/agenda.py` (the overlay).
Revisit when: A feature needs to list every item that was ever seen, not just those someone acted on; then the sparse rows can be back-filled or the table made full.
