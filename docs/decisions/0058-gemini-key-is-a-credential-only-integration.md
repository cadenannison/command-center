# 0058. The Gemini key is a credential-only "integration" of SettingsService, not a source

Status: accepted

Context: Task 2y. The summary reads `SecretStore` `("gemini", "api_key")` but nothing let a user set it (0053, item 7). A `SourceAdapter` needs `fetch`, and everything registered as one is synced by `sync_all`, the scheduler and shown in the agenda's sources.
Decisions:
1. `core/ports.py` gains `IntegrationAdapter` (`name`, `async validate`). `SettingsService(adapters, secrets, sync, integrations=None)` takes a second mapping. An integration is listed, connected (merged with the stored key, validated, stored) and deleted like a source with the same write-only status and redacted messages, but has no sync state (`sync` is `None`), no `mark_syncing`, no events to purge. `SyncService` is never given it, so `sync_all`, the scheduler, `POST /v1/sync` and the agenda cannot reach it. A name that is both is a `ValueError`. A sync is due exactly when `ConnectResult.sync` is not `None`; the API and web PUT handlers use that test.
2. `adapters/summary_gemini.GeminiIntegration` validates with `count_tokens` on the configured Gemini model: it needs a valid key, spends no generation quota, and reuses the file's client construction (`_default_client`, now with a `timeout_ms`). Timeout 15 s, enforced by the SDK's `HttpOptions` and by `asyncio.timeout`. 400, 401 and 403 mean a rejected key (Google answers an unknown key with 400; not exercised against the live API here, no key was available), 429/5xx/timeout/network are `TransientError`. All messages are fixed text and the SDK exception is dropped with `from None`; `SettingsService` then redacts and trims again. `app.build_integrations(settings)` registers it; `summary_model` is passed only when the provider is `gemini` (an Ollama model name is not a Gemini model).
3. `SummaryService` is unchanged. `GeminiSummaryProvider` already reads the key on every call (0036), so a saved key works without a restart and a deleted one falls back as before. A summary already stored for a day is kept after the key is deleted: removing it would need a delete on `SummaryStore` and `storage`, outside this card, and the stored text is the user's own data. "Not configured" therefore means: no new summary can be made (the provider fails with "Gemini API key is not set"), and a day without one gets the existing fallback of 0035/0040: the latest earlier day's stored summary (`provider` "stored"), else the template. After a delete, new days can therefore still show an old Gemini summary.
4. The opt-in is untouched (AGENTS rule 6, 0004): the key never turns summaries on, `CC_SUMMARY_ENABLED` does. The card says so. The Gemini card exists even while summaries are off or the provider is `ollama`, as the card asked. The project manager confirmed: `gemini` is registered always, never conditionally on `summary_enabled` or the provider. (Considered and rejected: registering it only when summaries are enabled with the Gemini provider, which would have kept the old wiring test green but hides the key entry until the user has set an environment variable.)
5. The web card is marked `SourceForm.credential_only`: status "Connected" when the key is set, no polling, a delete prompt about the key. The card text repeats the docs: free-tier prompts may be used to improve Google products, human reviewers may read them, personal data is redacted before sending (the old "(decision 0004)" suffix was dropped from the user-facing text).
6. `GET /v1/settings` gains a `gemini` entry with `sync: null`. No schema changed, so `docs/generated/openapi.json` has no new field; for the mobile repo the list has one more item.
Alternative: (a) A do-nothing `SourceAdapter` for `gemini` (0053 option c): it would add a fake source to `sync_all`, the sources list and every "N sources" assertion. (b) A `kind` field on `SourceSettings` to tell integrations apart: an API change for the mobile repo; `sync: null` plus a key already says it. (c) Make the key's presence the opt-in: contradicts rule 6. (d) Validate with `generate_content`: spends quota and sends a prompt for a check. (e) Delete cached summaries on key delete: needs a `SummaryStore` method and a storage change.
Reason: A separate small port keeps the sync path free of anything that cannot fetch, and reuses the settings flow, its write-only guarantees and its redaction instead of a parallel route.
Where: `core/ports.py`, `services/settings.py`, `adapters/summary_gemini.py`, `app.py`, `api/settings.py`, `web/settings_routes.py`, `web/sources.py`, `web/cards.py`, `web/templates/_card.html`; tests `test_gemini_integration.py`, `test_settings_integration.py`, `test_gemini_key_entry.py`, `test_app_integrations.py`.
Existing test: `tests/test_app_wiring.py::test_the_real_container_serves_an_empty_agenda_and_unconnected_settings_and_sync_states` asserted that `/v1/settings` lists exactly the five sources. The project manager approved changing only that assertion: `/v1/settings` must equal the five sources plus `{"source": "gemini", "keys": {}, "sync": None}`, last. `POST /v1/sync`, its states and `container.sync.sources()` stay at the five sources, because integrations do not sync. Test function names are left alone.
Revisit when: a second API-key integration appears (then a `kind` in the API may be worth it), summaries should be cleared with the key, or the Gemini 400 mapping is checked against the live API.
