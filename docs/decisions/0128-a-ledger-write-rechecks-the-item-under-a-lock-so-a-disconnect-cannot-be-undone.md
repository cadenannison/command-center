# 0128. A ledger write re-reads the item under a lock, so a note cannot outlive a disconnect

Status: accepted

Context: The reviewer found that `check_off` and `set_note` read the stored event, then insert a ledger row in a transaction that takes no lock. A disconnect deletes the events and then the ledger rows, each in its own transaction. If it committed between the read and the insert, the new row was not yet visible to its ledger delete, so a note or a `done_by = "user"` stamp survived the disconnect. The sink's leftover purge cannot clean it up because the sync state is already gone. In single-process mode there is no generation number to lock, so the sink's `lock_generation` (decision 0075) does not apply.
Decision: Creating a row is three steps in one transaction: read the event with `read_event(..., lock=True)`; insert the row and flush; read the event again with `lock=True`, and if it is gone, delete the row and report the item as not found. The flush takes SQLite's write lock, so a disconnect cannot commit its event delete until this transaction ends, and the second read sees one that committed earlier. On Postgres `FOR UPDATE` holds the event row, so the disconnect's delete waits until the commit and its ledger delete then sees the new row and removes it. This depends on the disconnect deleting events before ledger rows, which every purge path does. `read_event` always reads fresh from the database, never the session's cached row. A write to a row a disconnect deleted mid-update (`StaleDataError`) answers "not found", not a 500. A sync that made the same row between this write's read and its insert is a unique-key clash (`IntegrityError`): the write runs once more and the second try finds that row (round 2 of the review). Both are handled by `_tolerating_concurrent_writes`. On Postgres that same overlap could instead deadlock the sink's transaction against this one (the sink waits for the event row this write locked, this write waits for the sink's uncommitted row); Postgres aborts one of them, and this decision does not remove that case. A failed report is redelivered, so it is a delay, not a loss. The existing check: an item with no event is only written when it already has a ledger row (a note on an item that left its source stays).
Alternative: Take `lock_generation` for the event's source (it needs a generation, which single-process mode does not have, and makes every note write contend with syncs); `BEGIN IMMEDIATE` for every write on SQLite plus `INSERT ... SELECT ... WHERE EXISTS` (SQLite-specific, and Postgres needs the row lock anyway); a lock in the services (does not cover the sink's transaction or another process).
Reason: One re-read under the lock closes the window on both databases with no new table, no generation in single-process mode, and no change to the order of the purges. The cost is one extra indexed read when a row is created.
Where: `src/command_center/storage/sqlite_items.py` (`_known_row`, `_tolerating_concurrent_writes`), `src/command_center/storage/sqlite.py` (`read_event`); `tests/test_ledger_disconnect_race.py` (SQLite only: on Postgres the same interleaving blocks on the row lock, so it cannot be staged in one thread, and no test here covers that path).
Revisit when: A purge path deletes ledger rows before events, or a second ledger writer (the phone) is allowed to create rows; the interleaving then needs a Postgres test with two connections.
