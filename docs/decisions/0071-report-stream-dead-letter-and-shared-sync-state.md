# 0071. A report stream between workers and the normalizer, `JobQueue.dead_letter`, and a shared sync-state store

Status: accepted; item 5 (the api still writes state, and connect's in-process sync can race a report) is superseded by 0074

Context: Task 3b. A sync worker fetches events but, by the card, must not write them; the normalizer writes with `EventStore.replace` (0028). `Job` has no payload (0047), so fetched events need another channel. `SyncService` keeps `SyncState` per process in memory, which two processes cannot share. `JobQueue.fail` dead-letters only when attempts run out (0047), but a `FatalError` must dead-letter at once.
Decisions:
1. **`SyncReport` and `DeadReport` in `core/jobs.py`.** `SyncReport(id, correlation_id, source, window, status, message, at, events)` with status `ok | reconnect | error`; only `ok` may carry events (validator). `DeadReport` is the same without events, so a dead-lettered report never keeps event text. Both are frozen and `extra="forbid"`.
2. **`ReportStream` port** (`publish`, `consume(group, consumer, block_ms)`, `ack`, `dead_letter`, `list_dead_reports`) with `InProcessReportStream` (tests, hermetic chaos runs) and `RedisReportStream` (streams `{cc-reports}:reports` and `:reports:dead`, same consumer-group, XAUTOCLAIM and Lua-resolve design as 0047). A report delivered more than 5 times without an ack is dead-lettered with a fixed reason.
3. **`JobQueue.dead_letter(job, reason)`** added to the port and both queues: it moves the held delivery to the dead list at once. It is a no-op for a job not in flight.
4. **`SyncState` and `SyncStatus` move to `core/sync_state.py`**; `services/models.py` re-exports them, so existing imports keep working. A `SyncStateStore` port (`put`, `get`, `delete`, `user_id="local"`) and `SqliteSyncStateStore` (table `sync_states`, primary key `(user_id, source)`, the whole state as JSON text, `at` inside it) let the normalizer record state a second process can read.
5. **The normalizer is the only writer of worker results** in distributed mode: events a worker fetched and the sync state of that fetch. (One other writer remains: connecting a source in the api still runs an in-process `SyncService` sync that writes events directly and does not touch `SyncStateStore`, so a report fetched before the connect and applied after it can replace the newer events. Moving that sync onto the queue is the revisit trigger in 0070.) It calls `events.replace` for an `ok` report, then `states.put`, then acks. A crash between the two leaves the events replaced and the report unacked; redelivery replaces the same set and records the same state (tested in `test_chaos_distributed.py`). A `ValueError` from `replace` (a bad report) dead-letters the report; any other exception propagates unacked so the stream redelivers.
6. **Messages are redacted twice**: the worker words them, the normalizer passes them through `safe_message` before storing (0052, 0056). Reports carry events only, never credentials (jobs carry none either).
Alternative: (a) Put the events in the job: needs a payload on `Job`, changes 0047, and puts event text in the job dead-letter list. (b) Let the worker call `EventStore.replace` itself: two writers per source and no single place for idempotence. (c) Use only `fail` and a non-retryable reason: `fail` would still spend attempts. (d) A shared SQLite or Postgres table written by the worker: couples workers to storage, which the import rules forbid (workers import services and core only).
Reason: one writer per table, a retry that cannot duplicate, and a dead letter that holds no event text.
Where: `core/jobs.py`, `core/sync_state.py`, `core/ports.py`, `adapters/inprocess_queue.py`, `adapters/inprocess_reports.py`, `adapters/queue_redis.py`, `storage/sqlite_states.py`, `workers/normalizer.py`; tests `test_job_queue_dead_letter.py`, `test_report_stream_contract.py`, `test_sync_state_store.py`, `test_normalizer.py`.
Unverified: `RedisStreamsQueue.dead_letter` and `RedisReportStream` were written without a Redis server in the build sandbox. The contract tests are parametrized on both backends and run against Redis when `CC_TEST_REDIS_URL` is set; run them once before relying on it.
Revisit when: reports get large (a payload store plus a reference); the api reads `SyncStateStore`; a second event consumer appears (then the stream needs more than one group).
