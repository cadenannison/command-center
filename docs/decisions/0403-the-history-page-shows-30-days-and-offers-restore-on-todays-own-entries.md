# 0403. The History page shows 30 days and offers Restore on today's own entries

Status: accepted

Context: Card A1b replaces the History placeholder. 0334 says History lists Done and Dismissed by day, newest first, with counts, search and All / Done / Dismissed filters, and that Restore is for today's items. It does not say which entries count, how far back to ask, or what Restore means for an item the source finished.
Decision:
- The page (`ui/src/features/history/`) asks `GET /v1/history` for the last 30 local days, today included, and shows days newest first and entries newest first. Each day has an `h2` heading ("Thursday, Nov 12") and its whole-day counts ("2 done, 1 dismissed"), which do not change with the filter or the search. An entry shows the title, the outcome as text (Done, Dismissed, Gone) and the time; a note, if there is one, is shown under the title. Titles and notes are `data-sensitive` (0396).
- Done is the `done_by_you` and `done_by_source` lists, Dismissed is `dismissed`, and an entry with outcome `gone` shows under All only (the filters are the three the card names).
- Search is client-side over the loaded entries (title and note, case-insensitive). The filter and search are page state and survive a refetch.
- Restore is offered on today's entries in `done_by_you` and `dismissed`. Not on older days (0334), not on `gone`, and not on `done_by_source`: restore leaves an item the source finished done, so the button would do nothing. "Today" is the browser's local day, the same day the summary uses. Restore uses the shared hook (0402) and its "Restored." toast, which has no Undo of its own.
- States: loading, empty ("Nothing done or dismissed in the last 30 days."), "Nothing matches." for a search with no hits, an error with Retry (fixed text), and, when a refresh fails while data is on screen, the 0375 notice with Retry. No server text is shown. A body that is not the shape the page reads (not an array, a day without its date, a list that is not an array, an entry without id, title, time, group or outcome) is the same error state, thrown in `fetchHistory` before the page sees it; it never crashes the page.
- After a Restore, once the refetch has settled and the entry is gone, focus moves to the next restorable entry's Restore button, or to the page heading (`tabindex="-1"`) when there is none, so a keyboard user does not lose their place. Row keys do not use a list index, so a row keeps its key when another leaves.
- Restore on older days is enforced only by the UI. The service restores an item on any day (`services/items.py`), so a direct call to `POST /v1/items/{id}/restore` is not limited to today. 0334 calls it a service rule; a backend follow-up card will enforce it there. Until then the rule is a button that is not shown, not a guarantee.
Alternative: Restore on every entry (rejected: 0334 limits it to today). Restore on source-done entries (rejected: it is a no-op). A longer or open-ended range with "Load more" (rejected for this card: client-side search is over what is loaded, and the card adds no paging). Counts that follow the filter (rejected: a day's heading should say what the day held).
Reason: The buttons shown are the ones that change something, and the window is one the API accepts in one request.
Where: `ui/src/features/history/history-page.tsx`, `history-model.ts`, `use-history.ts`; the route in `ui/src/router.tsx`.
Revisit when: Restore should reach older days, History needs paging or a date range, or the day should follow the server's timezone rather than the browser's.
