# 0086. `purge` bumps the generation a second time, so a disconnect ends on the stored number plus two

Status: accepted

Context: Task 4d, closing the first open decision of 0085. A disconnect runs `cancel` (bump), deletes the credentials, then `purge`. A sync queued between the bump and the credential delete (a scheduled round, `POST /v1/sync`, a connect's follow-up) is stamped with the number the bump produced, so the normalizer does not drop its report: if the worker read the credentials before they were deleted, the events and state come back after the purge.
Decision: `QueuedSyncService.purge` calls `GenerationStore.bump(source)` before it deletes events and state. The enqueuer reads the generation before the credentials (`SyncEnqueuer.publish_outcome`), so a job that saw the credentials was stamped before the credentials were deleted, which is before this second bump, and its number is below the current one when its report arrives. A disconnect now ends on the number it started on plus two; a repeated disconnect adds two more. Nothing depends on the absolute value: jobs and reports compare for equality with the current number, and a reconnect after a disconnect queues its job with the new number.
Test changes (the card allows these two, in `tests/test_distributed_connect.py` only): `test_disconnect_purges_events_and_state_and_bumps_the_generation` now expects 2 instead of 1, and `test_a_reconnect_after_a_disconnect_queues_a_job_with_the_new_generation` expects a job with generation 2 instead of 1. Both numbers moved only because of the second bump. New tests, `tests/test_purge_generation.py`: `purge` bumps once more, and a report whose job was queued between `cancel` and `purge` is dropped (events and state stay empty); both failed before the change.
Alternative: (a) Bump once, at the end of the disconnect, after the credentials are deleted: the abort-before-delete property of 0085 is lost, because the bump is what has to come first so a failure there deletes nothing. (b) Make the normalizer drop reports for a source with no credentials: it has no secret store, and adding one to it widens its trust. (c) Hold a lock across the three steps: the api and the workers are separate processes with no shared lock besides the database; the bump is that lock.
Reason: two bumps cost one extra row update and close the window with no new state. The first bump keeps its job (abort before anything is deleted); the second bump is placed after the credentials are gone, which is the only point from which no new job can see them.
Where: `src/command_center/services/queued_sync.py` (`purge`); `docs/contracts/services.md`, `docs/contracts/api.md`, `docs/distributed-mode.md` (the failure table and Known gaps); tests `tests/test_purge_generation.py`, `tests/test_distributed_connect.py`.
Not done: three existing tests in `tests/test_settings_disconnect_order.py` encode the old count of bumps and fail now: `test_disconnect_bumps_the_generation_then_deletes_secrets_then_purges` (the journal is now `bump, delete_secrets, bump, delete_events`), `test_a_failed_purge_after_the_secrets_are_gone_says_the_disconnect_is_incomplete` (the number after a failed purge is 2, not 1; the second bump runs before the events delete that fails) and `test_a_retried_disconnect_completes_after_a_failed_purge` (4 after the retry, not 2). The card does not allow edits to that file, so they were left as they are; they need the file added to the allowance, or the card amended.
Revisit when: a sync can be queued after the credentials are deleted by a path that does not check them (`publish_one` for the connect follow-up still does not; its `reconnect` row is the gap in `docs/distributed-mode.md` for a quick disconnect after a connect).
