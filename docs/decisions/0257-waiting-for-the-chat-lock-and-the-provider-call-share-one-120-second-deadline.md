# 0257. Waiting for the chat lock and the provider call share one 120-second deadline

Status: accepted. Builds on 0223 (the other fixed-text failures of a provider call) and 0225 (the adapters' per-read timeout).

Context: The adapters' httpx timeout is per read, so a server that sends a few bytes now and then never trips it, and the single chat lock stays held. Every other message, and the AI card's test button, then waits behind it with no limit. A first fix wrapped only the provider call in `asyncio.timeout`; a message queued behind a slow call could then wait one deadline for the lock and another for its own call.
Decision: One constant, `CALL_TIMEOUT_SECONDS = 120.0` in `services/chat.py`, bounds lock acquisition plus everything under the lock (settings reads, context build, provider call) in `reply` and `test_connection`, through one `asyncio.timeout` in `ChatService._deadline`. On expiry the call raises `ChatUnavailableError("failed", "The chat provider did not answer in time")`; the lock is released by leaving the `async with`; the conversation store is written only after the answer, so a timed-out message keeps nothing. No caller waits longer than one deadline in total. The web pages' htmx timeout is 135 s, a little over, so the server's fixed text arrives before the browser gives up.
Alternative: 90 seconds, as the card suggested ("about 90 s"). Not taken: the adapters' per-read timeout is 120 s (`chat_http.TIMEOUT_SECONDS`), and a local Ollama that has to load a model can take longer than 90 s before its first byte, so 90 s would cut off answers that work today. 120 s makes the new bound equal to the old per-read bound, so no call that succeeds now starts failing; a test pins the deadline at or above the adapters' timeout. A separate timeout for the lock wait and one for the call (rejected: two numbers, and the total is then up to their sum). Cancelling the provider task from outside (rejected: `asyncio.timeout` already cancels it).
Reason: The goal is a bound on the total wait, not a short one. Equal to the existing per-read bound is the smallest change that gives a bound.
Consequences: A user can wait up to two minutes for a failure; the fixed text says so. The deadline starts after the rate-limit slot is taken, so a message that times out still counts against the limit (as an answered one does, 0180).
Where: `services/chat.py` (`CALL_TIMEOUT_SECONDS`, `_deadline`, `reply`, `test_connection`); `tests/test_chat_call_deadline.py` (never answers, trickles, waits for the lock, `/ai/test`, 135 s page timeout); `docs/contracts/services.md`, `docs/contracts/web.md`.
Revisit when: The adapters get a streaming reply with its own idle timeout, or a provider is routinely slower than two minutes (then raise it here and in the pages' 135 s together).
