# 0131. Completions are an append-only table; an item's state is derived

Status: accepted. Supersedes the limitation and open question of 0130 (0130 keeps `reopened_at` and the permanent history).

Context: Decision 0130 kept one completion per item in `item_ledger.done_at` and `done_by`. The reviewer found two consequences: you cannot check off an item the source completed and then reopened (the row still says "done by source"), and a second source completion could not be recorded. The project manager approved option (c), a completions table.
Decision: `item_completions` holds one append-only entry per completion: `(user_id, item_id, completed_by, completed_at)` with `completed_by` `source` or `user`; that four-column primary key makes recording the same completion twice a no-op (the column is `completed_by` because `by` is an SQL keyword). Rules: a sync appends a `source` entry on each open-to-done change it sees (`record_sync` appends unless the latest `source` entry is still current, that is no reopen at or after it); a source reopen sets `item_ledger.reopened_at` and leaves every entry alone; a user check-off appends a `user` entry (a second one while one stands is a no-op); an undo deletes that item's `user` entries only, because it corrects a mistake and is not a record of what happened; a disconnect deletes the entries of the source's items; deleting a local task deletes its entries. An item's state is derived, never stored: done when it has a `user` entry or the source currently reports it done (the event's own status), otherwise open (`overlay_marks` applies a user entry only). History lists every entry on its completion day, and a `source` entry is `reopened` when the row's `reopened_at` is at or after its time, so only entries a reopen followed are tagged. `marks` reports the `user` entry if there is one, else the latest `source` entry. A check-off locks its row before it appends, so a disconnect cannot leave an entry for a deleted item (decision 0128). Migration: `ensure_ledger_schema` creates the table and, in the same transaction, copies one entry from each `item_ledger` row that has `done_at` and `done_by`; it copies only when it creates the table, so running it twice, or at every start, never repeats it and never brings back a check-off that was undone afterwards. The old `done_at` and `done_by` columns stay in `item_ledger` and stay readable, but nothing writes them. The ledger row stays sparse: it exists while there is a note, an entry or a removal.
Limitation: the key has no sequence number, so two entries of one item by the same side at the same instant are one entry (a source that completes, reopens and completes again inside one sync clock tick). The clock advances between real syncs, and tests advance it. A sync that missed the reopen (the item was open only between two syncs) records no second entry. A completion made at the very instant of the reopen before it is shown with `reopened: true` although the item is done (`reopened_at >= completed_at` is needed for the same-instant done-then-open case).
Alternative: Keep one completion per row and let a check-off take over a reopened row (moves the history entry, breaks permanence); add user-completion columns beside the source's (a second one-completion-per-side limit and still no second source entry); put a generated id or a sequence in the key (needs an id source for no gain, the time is the order); make undo a tombstone (keeps a record of a mistake).
Reason: One row per fact is the model that holds all four cases (second source completion, check-off after a reopen, undo of only your entry, permanent history), and deriving the state removes the stored "done" flag that went wrong in 0129 and 0130.
Where: `src/command_center/storage/sqlite_ledger_tables.py` (tables), `sqlite_completions.py` (queries, `ensure_completions_table`), `sqlite_ledger.py` (`record_sync`, `ensure_ledger_schema`, `delete_source_ledger`), `sqlite_items.py` (`check_off`, `undo`, `marks`, `history`, `remove_local`); tests in `tests/test_ledger_completions.py` (SQLite and, with `CC_TEST_POSTGRES_URL`, Postgres), `tests/test_ledger_sync.py`, `tests/test_ledger_migration.py`. Mobile contract: no new field; an `item_id` can now appear in several history entries (`docs/mobile-api-notes.md`).
Revisit when: A history view needs to tell two completions at one instant apart, or the old `done_at` and `done_by` columns can be dropped (after every deployment has migrated).
