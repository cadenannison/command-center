# 0301. The UI supply-chain policy: pinned pnpm, frozen lockfile, blocked install scripts, release age, audit, an approved list and a strict CSP

Status: accepted

Context: An npm dependency tree is the largest supply-chain surface this repo has had; the Python side has about 130 locked packages, a typical Vite and React tree has hundreds. Install scripts, freshly published malicious versions and typo-squatted names are the usual routes in. The app handles calendar, email and Canvas data, and models invent plausible package names (AGENTS.md).
Decision:
1. Package manager: pnpm only, pinned twice and checked to agree: `packageManager` in `ui/package.json` (name, exact version and hash) and the `pnpm` tool in `mise.toml`. Node 26 does not bundle corepack, so mise provides pnpm; `ui:setup` fails if the two versions differ. The version is chosen by the scaffold task and must be at least 14 days old when pinned. Nothing is pinned by this record: on 2026-11-10 the registry's latest was 12.18.0, and the published package of 11.28.9 (27 October) was inspected and contains the settings named below, so it is a candidate.
2. Lockfile: `ui/pnpm-lock.yaml` is committed. Every install outside a task that adds a dependency is `pnpm install --frozen-lockfile --ignore-scripts` (CI, `ui:setup`, the Docker build). Nothing resolves versions in CI.
3. Install scripts blocked: dependency lifecycle scripts (`preinstall`, `install`, `postinstall`) do not run. Installs pass `--ignore-scripts`, and `ui/.npmrc` or `ui/pnpm-workspace.yaml` leaves the build allow-list empty (`allowBuilds`, called `onlyBuiltDependencies` in older pnpm; use the name the pinned pnpm documents) with `strictDepBuilds` on where supported, so an unreviewed build script fails the install. A package that genuinely needs a build step (for example a native binary downloader such as esbuild's) is listed there only with a note on its line in `docs/approved-dependencies.md` stating why. `blockExoticSubdeps` (no git or tarball-URL transitive dependencies) and `trustPolicy: no-downgrade` are turned on where the pinned pnpm supports them.
4. Minimum release age: set `minimumReleaseAge` (pnpm 10.16 and later; minutes) to 10080 (7 days), matching the Dependabot cooldown already used for uv and Actions. The package of pnpm 11.28.9 contains `minimumReleaseAge`, `minimumReleaseAgeStrict` and `minimumReleaseAgeExclude`; the scaffold task must still confirm the pinned pnpm honours the setting by test (an install of a version younger than the age must fail, so set `minimumReleaseAgeStrict` if the default only warns or picks an older version); if it does not, the pin moves to one that does, or this record is superseded with another control. `minimumReleaseAgeExclude` stays empty.
5. Audit: `pnpm audit --prod --audit-level high` runs in the CI `audit` job through `mise run audit` (an advisory job, not part of the gate, same as pip-audit), with a second pass over dev dependencies that reports without failing.
6. Approved-dependency list: kept in `docs/approved-dependencies.md`, a file only the human edits (CODEOWNERS and the `.claude/settings.json` deny list enforce it, because the list is what the guard trusts). A dependency not on it needs the project manager's approval before it is added; the project manager records the approval by adding one line to that file. Each name is verified on the npm registry first (age, weekly downloads, repository, maintainers), as AGENTS.md requires for PyPI. `ui/package.json` is the declared set. `bash scripts/ui.sh guard`, run by `ui:check` and the CI `ui` job, fails on a name (dependencies, dev, optional and peer) that has no entry line in the file (a `@scope/*` entry covers a whole scope), on a version that is not exact, on `overrides`, `resolutions`, `packageExtensions`, `patchedDependencies` or a `.pnpmfile` (code that runs at install even with scripts off), and on a build allow-list entry that is not on the list. The hook `scripts/hooks/guard-bash.sh` blocks `pnpm add`, `pnpm dlx`, `npx`, `npm install` and a `pnpm install` without `--frozen-lockfile --ignore-scripts` for agents.
7. Strict CSP: the app sends a `Content-Security-Policy` for the UI: `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. No `unsafe-inline`, no `unsafe-eval`, no third-party origins, no CDN fonts or scripts. The UI therefore has no inline script or style: Vite builds hashed files and Tailwind emits a stylesheet. Adding the header is an api-layer task; the Jinja pages keep their own rules (decision 0212 records the inline listener that blocks a CSP there).
8. Vite dev server: `server.host` is `127.0.0.1`, `server.allowedHosts` is an explicit list (`localhost`, `127.0.0.1`), never `true`, and `server.cors` stays off. The proxy to the API targets 127.0.0.1 only.
9. No secrets in the bundle: no `VITE_` variable holds a credential (Vite embeds them in the client). The settings API stays write-only (AGENTS.md rule 5); the UI never holds a token it could print.
Alternative: Trust the registry and run `pnpm install` (rejected: the install-script route is the most common npm compromise). Vendor `node_modules` (rejected: large, and a lockfile with hashes gives the same reproducibility). Skip the release-age setting (rejected: it is one line and the Python side already does this). Keep the approved list inside this record (rejected: the list changes with every new dependency, and records are not edited after acceptance; a human-edited file read by the gate fits, and an agent-proof file is easier to protect than part of a record).
Reason: Each control removes one way a bad package runs on this machine: a pinned manager, a frozen and hashed lockfile, no install-time code, a delay for fresh versions, an advisory check, a human-approved name list (a file the gate reads), and a CSP and host restriction that limit what a compromised bundle or a hostile web page could do.
Consequences: Adding a dependency is slower by design. Some tools need an `onlyBuiltDependencies` entry and a note. The CSP means no inline script or style in the UI, ever. The audit job can go red on a new advisory without blocking a merge, as pip-audit does.
Hedge: which file pnpm 11 reads each setting from (`.npmrc` or `pnpm-workspace.yaml`) is not confirmed here; the guard accepts either and requires every assignment of a setting, in both files, to be safe (so a safe value in one file cannot hide an unsafe one in the other), and the scaffold task confirms by test that each setting takes effect. Not checked by the guard: the contents of `ui/pnpm-lock.yaml` (a non-registry resolution or an added transitive package passes it); that is reviewed by the human in the lockfile diff until a decision adds a lockfile check.
Where: `ui/package.json`, `ui/.npmrc`, `ui/pnpm-lock.yaml` and `ui/vite.config.ts` (later task); `scripts/ui.sh` (the `guard` and `audit` checks), `scripts/hooks/guard-bash.sh`, `mise.toml` and `.github/workflows/ci.yml` (the K1 guard patch, applied by the human); `docs/approved-dependencies.md` (the list, edited only by the human); `docs/decisions/0212-one-global-htmx-error-listener-is-inline-in-the-base-template.md` (the Jinja CSP note).
Revisit when: The scaffold task pins pnpm and tests the release-age setting; a dependency outside the list is proposed; a pnpm release changes how install scripts or release age work; or the CSP needs a nonce.
