# 0078. The smoke and report scripts exist for the human to run, and promise never to print a secret

Status: accepted

Context: Task 4b. Nothing here could start the Docker stack (no Docker in the sandbox that writes this code), and the project manager needs a way to see what a real first run did without being handed credentials. Two shell scripts close that gap: `scripts/smoke-distributed.sh` (the human runs it against a running compose stack) and `scripts/report-state.sh` (the human runs it against any running app and pastes the output).
Decision:
1. `smoke-distributed.sh` drives the stack only through the api's public routes and `docker compose --env-file`: health, connect weather, sync, wait for `ok` (60 s), count the weather events, kill and start `worker-weather` and sync again (count unchanged), kill and start the normalizer (state and count unchanged), disconnect weather (events and state gone, and still gone after another normalizer restart). It prints a PASS or FAIL line per step and exits 1 if any step failed. Weather is the source because it needs no account.
2. What the scripts never print: a credential or any value of one, the coordinates sent to weather, a request or response body, an event title, a URL, the contents of the compose env file, or an environment variable. They print step names, counts, statuses, source and key names, and for report-state the last 4 characters of a key exactly as the api returns them.
3. How that is kept: smoke never reads the env file (it checks it exists and hands its path to compose through one function, `dc`, so every compose call has `--env-file`); the connect body goes through a file, not a command line; there is no `set -x`, no `curl -v`, no `cat` of a body. report-state reads only `GET /v1/settings` and `GET /v1/events`, which carry no credential, and still treats them as untrusted: it prints a fixed set of fields, cuts each last-4 to 4 characters, shows a key or source name only if it is plain lower-case snake_case (else `?`), accepts only the four known statuses, and masks URLs, email addresses, token-like strings (12 or more characters with a digit, `-` or `_`) and digit runs of 6 or more in the message, then cuts it to 200 characters. The mask runs before the cut, so a cut cannot leave half a token.
4. Smoke refuses to run when weather is already connected, so it can never overwrite a real connection or delete it at the end. If it stops after connecting, it disconnects its own connection on exit.
5. The tests (`tests/test_smoke_distributed_script.py`, `tests/test_report_state_script.py`) run no Docker: they check the script text (executable, `set -euo pipefail`, no tracing, no secret-named variable, `--env-file` on every compose call) and run report-state against a stub `curl` fed a response that holds a `fake-` token in a message, in a last-4, in a key name, in a status and in an extra field, and assert the token (and everything but its last 4 characters, and the string `fake-`) is absent from the output. The hostile response is deliberately not built through the pydantic models, because it breaks their schema on purpose.
Alternative: (a) Put the checks in pytest against the compose stack: needs Docker in CI and is a poor place to restart containers. (b) Have report-state read the logs, the keychain or the secrets file for more detail: that is where secrets are, and the point is that the output is safe to paste without reading it. (c) Trust the api's redaction alone and print `message` and `last4` as received: a single bug in the api would then reach a chat; the extra masking costs a few jq lines. (d) Mask everything not on an allow-list of messages: the messages are free text from adapters and an allow-list would hide real errors.
Reason: the human is the only one who can run Docker and hold credentials; the scripts make a real run reproducible and its result pasteable. The api's own redaction (decision 0052) is the first line; the script's masking is the second, so that neither one's failure alone puts a secret in the output.
Where: `scripts/smoke-distributed.sh`, `scripts/report-state.sh`, `docs/first-run.md`, `docs/distributed-mode.md` (Smoke test); tests as above.
Limits: masking is by shape, not by knowledge of the secret. A short secret that looks like a word in a message would pass the second line; only the api's redaction stands behind it. The smoke script has been syntax-checked and shellchecked but not run against a real stack. A scheduler round landing during the normalizer restart can change the sync time and fail the "state unchanged" step; run it again.
Revisit when: the api gains a version or build route (report-state reads the version from `pyproject.toml` today), the stack is run in CI with Docker, or a source's messages need a rule the shape-based mask cannot give.
