# 0315. pnpm 12.14.0 is pinned, and its supply-chain settings live in ui/pnpm-workspace.yaml, not .npmrc

Status: accepted

Context: Decision 0301 leaves the pnpm version and the file each setting is read from to the scaffold task (P1a), and names 11.28.9 (published 2026-10-27) as a candidate. The registry listing taken on 2026-11-11 shows two release lines in parallel: 11.28.x and 12.x. A pnpm 12.14.0 binary is installed on this machine, so its behaviour can be tested here; 11.28.9 would need an install, which this task may not do.
Decision:
- Pin pnpm 12.14.0 (published 2026-10-15, 27 days old; the rule is at least 14). `ui/package.json` `packageManager` is `pnpm@12.14.0+sha512.<hex>`, where the hash is the registry's `dist.integrity` for `pnpm-12.14.0.tgz` converted from base64 to hex (`c18ba6d8...89a6`). `mise.toml` pins `pnpm = "12.14.0"` (the K1 guard patch follow-up `p1a-guard.patch`; the human applies it). The guard checks the two agree.
- Put `ignoreScripts`, `saveExact`, `minimumReleaseAge: 10080`, `minimumReleaseAgeStrict: true`, `minimumReleaseAgeExclude: []`, `strictDepBuilds`, `blockExoticSubdeps` and `trustPolicy: no-downgrade` in `ui/pnpm-workspace.yaml`, camelCase, one key per line, no `packages` key. `ui/.npmrc` is not created. `allowBuilds` is not written (an empty map would trip the guard; `ignoreScripts` and `strictDepBuilds` cover the build step).
- Why not `.npmrc`: tested with the pnpm 12.14.0 binary in a scratch project, `pnpm config get` returns the value for each of those keys when set in `pnpm-workspace.yaml` and `undefined` when the same keys (kebab-case or camelCase) are set in `.npmrc`. pnpm's own changelog says `.npmrc` is for registry and auth settings. The guard accepts either file, so a safe-looking `.npmrc` would pass the guard while pnpm ignored it; that is the trap this choice avoids.
- `minimumReleaseAgeStrict: true` is set explicitly. The 12.x changelog says it defaults to true when `minimumReleaseAge` is explicitly configured, but an explicit value does not depend on that.
Alternative: 11.28.9, the 0301 candidate (not taken: it cannot be exercised here, and 12.14.0 can). 12.16.1, the newest at least 14 days old (not taken: not the version installed locally, so nothing could be tested; the gain is only newer fixes). Settings in `.npmrc` (rejected: ignored by pnpm 12.14.0, see above). Both files (rejected: two places to keep in step for no effect).
Reason: A setting that the guard accepts but pnpm ignores gives false assurance, so the file was checked against the real binary. The pin is one the project manager can test the same way.
Consequences: Enforcement of `minimumReleaseAge` (an install of a too-new version failing) is not yet shown by test, only that pnpm reads the setting; see Hedge. The lockfile `ui/pnpm-lock.yaml` and `ui:check` passing wait on the human: the guard requires a lockfile, and agents may not create or edit it. A Dependabot entry for `/ui` with a 7 day cooldown is in the patch.
Hedge: not verified here, because no package may be installed in this task: that an install of a version younger than 10080 minutes fails under `minimumReleaseAgeStrict`; that `strictDepBuilds` makes an unreviewed build script fail the install; that `blockExoticSubdeps` and `trustPolicy` behave as 0301 describes; that mise provides pnpm 12.14.0 and that the machine's binary is byte-identical to the registry tarball whose hash is pinned (pnpm's own `packageManager` check will fail loudly if not). The first install by the human is the test.
Where: `ui/package.json`, `ui/pnpm-workspace.yaml` (in `p1a-guard.patch`, because agents may not write it), `mise.toml` (patch).
Revisit when: The first install runs (record the result of the enforcement checks on this record's Hedge line by a new record), pnpm 12 changes where settings are read, or the pin moves.
