# 0398. Dismiss, snooze and restore are ledger state on the item id, and the latest action wins

Status: accepted

Context: Decision 0334 settled that dismiss is a ledger state beside done and that restore exists, but left open how snooze fits, how the actions interact and how a sync leaves them alone. Card A1a builds the backend.
Decision: `item_ledger` gains two nullable columns, `dismissed_at` and `snoozed_until`, keyed on the existing (user, item id) row, so a sync that replaces the event row cannot touch them. Dismiss stamps `dismissed_at` (repeating it keeps the first time) and ends a snooze and the user's check-off. Snooze sets `snoozed_until` (repeating it replaces the time) and ends a dismissal. Check-off ends a dismissal and a snooze. Restore clears the snooze and the dismissal and removes the user's check-off; an item the source finished stays done, because that is the source's word (as with undo). Snoozed items are not in History; dismissed ones are. A dismissed item that later leaves its source is not also recorded as "gone". A row with a dismissal or a snooze is never dropped as empty, so a row whose `snoozed_until` has passed stays until the next action on the item (harmless, accepted). An item the source finished and the user then dismissed is shown once in History, as the dismissal; restoring it shows the source completion again, and a source completion after the dismissal is the later action and shows instead. Disconnecting a source removes its dismissals with its other ledger rows, notes included (decision 0127), so dismissed items return after a reconnect. The migration adds both columns with the same guarded ALTER as `reopened_at`, so it works on SQLite and Postgres; no index, because a migrated table must match a fresh one and the ledger is small.
Alternative: A separate `item_states` table (rejected: a second key to keep in step with the ledger row and its locks). Keeping a dismissal and a check-off both (rejected: History would show one item twice). Deleting the ledger row on snooze expiry with a job (rejected: the expiry is just a comparison against the clock, so nothing needs to run).
Reason: One row per item already carries the notes and the sync's memory, with the locking from 0121 and 0128; the new state rides on it. "Latest action wins" keeps each item in exactly one state.
Consequences: Additive columns; `ItemLedger` gains `dismiss`, `snooze`, `restore`; `ItemMark` and `Event` gain `dismissed_at` and `snoozed_until` (additive to openapi.json, 0302). An expired snooze leaves a stale `snoozed_until` in the row until the next action; it is never shown.
The ledger row is read fresh, after the event row is locked, by every write including restore, so the later of two racing writes decides on what the first committed (0401).
Where: `core/ledger.py`, `core/ports.py`, `storage/sqlite_ledger_tables.py`, `storage/sqlite_ledger.py`, `storage/sqlite_items.py`, `services/items.py`, `api/items.py`. Tests: `tests/test_dismiss_snooze.py`, `tests/test_dismiss_snooze_api.py`.
Revisit when: restore should reach history older than today (0334), dismissals should expire, or a custom snooze time is added.
