# 0412. A paired phone reads only what is on an allowlist

Status: accepted

Context: `remote_may_call` allowed every GET except two named paths, so each new route was readable by a paired phone until someone remembered to deny it. A phone could already read key status (`GET /v1/settings`, last four characters), the device list, the done history with notes, the web pages and the API docs (audit X05 and R15; card 08).
Decision: a paired phone may read only the routes in `REMOTE_READS` in `api/policy.py`: `/v1/tasks`, `/v1/dashboards`, `/v1/dashboards/{dashboard_id}`, `/v1/display-settings`, `/v1/agenda/{period}`, `/v1/events`, `/v1/attention`, `/v1/summary` and `/v1/needs-me`. The one write stays `POST /v1/sync`; `/v1/health`, `/v1/pair` and `/v1/pair/refresh` stay open without a token. Everything else is refused after the token check: 403 on `/v1`, 404 on the web UI's own routes (decision 0060), 401 with no token. That includes `/v1/history`, `/v1/settings`, `/v1/devices`, `/`, `/week`, `/month`, `/history`, `/settings`, `/pair`, `/chat`, `/static`, `/docs`, `/redoc`, `/openapi.json`, and any route not yet written. A `{name}` in an entry matches exactly one whole path segment; a prefix, a trailing slash, an empty segment, `.` or `..` never matches. Methods: GET, HEAD and OPTIONS on a listed path.
Alternative: keep the deny list and add paths to it (not taken: it fails open, so the next route is exposed until someone notices). Also not taken: an empty `REMOTE_DENIED_READS`. `tests/test_chat_remote_policy.py` imports it and asserts the chat preview is in it, so it stays with its two paths, checked first as a second lock.
Reason: a phone is reachable from the tailnet with a 15-minute token, and a stolen phone should reach only what its screens render. Settings and devices describe the security set-up and the web pages are the Mac's own; the app needs neither. `/v1/needs-me` was checked against the agenda: it is built from the same rows as `/v1/tasks` and projects them to a subset of the fields `/v1/events` already serves (`id, kind, title, source, at, link, priority, reasons`; no `raw`, no note flag), and it drops done, dismissed and snoozed items, so it exposes nothing a listed read does not.
Consequences: a breaking change for the mobile repo. Any call to `/v1/history`, `/v1/settings`, `/v1/devices` or a web page now answers 403 or 404, and the app must stop reading them (announced in `docs/mobile.md` and `docs/mobile-api-notes.md`). No route is renamed or removed and `openapi.json` does not change. A new phone read is a one-line change to `REMOTE_READS` plus its row in `tests/test_remote_policy.py`. Existing tests that used `/v1/settings`, `/v1/devices` or `/history` as a "phone is served" probe now use `/v1/tasks`; those about the denied routes assert the denial.
Where: `api/policy.py` (`REMOTE_READS`, `remote_may_call`); tests in `tests/test_remote_policy_allowlist.py` and the table in `tests/test_remote_policy.py`.
Revisit when: the phone app needs a screen that reads a route not listed, or card 09 (the policy proven through the real app) finds a route whose answer differs from the table.
