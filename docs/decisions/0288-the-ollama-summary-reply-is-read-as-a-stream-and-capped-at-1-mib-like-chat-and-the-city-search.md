# 0288. The Ollama summary reply is read as a stream and capped at 1 MiB, like chat and the city search

Status: accepted. Extends 0222 and 0246, which capped the chat reply and the city search reply but left `summary_ollama.py` on `client.post`.

Context: `OllamaSummaryProvider.summarize` called `client.post`, which reads the whole body into memory before any check. The endpoint is local and fixed, but a misbehaving or replaced local server (or one the user pointed `base_url` at) could still fill memory, and chat to the same Ollama server already had the cap. `adapters/CLAUDE.md` also said all outbound HTTP used `http_cap.py`, which was untrue for most paths.
Decision: `summarize` opens `client.stream("POST", ...)`, decides the status from the headers (an error page is never read), and reads the body with `http_cap.read_capped`, the one shared implementation (1,048,576 decoded bytes; a declared `Content-Length` over it is refused before any read; a chunked reply with no length is abandoned at the cap). A reply over the cap is `SummaryProviderError("Ollama sent a reply that is too large")`, with no prompt, URL or body in it. The JSON is then parsed from the bytes with `json.loads`; a body that is not JSON or not an object with a string `response` is still "Ollama returned a malformed summary". `SummaryProviderError` and `SummaryRateLimited` raised inside the stream block pass through the catch-all unchanged. Timeout, connection and any-other-exception handling, and `trust_env=False`, are as before (0245, 0246). `adapters/CLAUDE.md` and `docs/contracts/adapters.md` now list exactly which adapters use `http_cap.py` (`chat_http`, `weather_geocode`, `summary_ollama`), `net_guard.py` and `trust_env=False`.
Alternative: Keep `client.post` and check the length afterwards (rejected: the body is already in memory). Cap through a different limit for summaries (rejected: a summary is a short JSON object, and one constant keeps the callers from drifting). Move the Gemini SDK path to the cap too (not possible: the SDK owns its transport).
Reason: One cap, one implementation, on every httpx path that talks to a model server, as the card asked.
Consequences: An existing test, `tests/test_summary_provider_hardening.py::test_ollama_summary_does_not_swallow_a_cancellation`, stubs `AsyncClient.post`, which the provider no longer calls, so it now fails with "Ollama is unreachable" instead of seeing the cancellation. The card said `tests: new-only` and AGENTS.md forbids editing it, so it is left as it is and reported; the same behaviour is covered by a new test on `stream` in `tests/test_summary_ollama_cap.py`. The project manager should allow the one-word change (`post` to `stream` in that stub) under a `tests: modify` card. A reply that does not decode (`httpx.DecodingError`) is still reported as "unreachable", as before; the geocoder maps it to its own text, and this one does not.
Where: `src/command_center/adapters/summary_ollama.py`, `src/command_center/adapters/CLAUDE.md`, `docs/contracts/adapters.md`, `tests/test_summary_ollama_cap.py`.
Revisit when: A summary legitimately needs a reply over 1 MiB, or the Gemini summary path gets its own cap (needs its own decision).
