# 0075. The generation is stored with the rows, and a report is checked and written in one transaction

Status: accepted

Context: Task 3f, resolving the two open questions of 0074. (1) A normalizer that died (or lost its database) between writing a report and its second generation check left the write behind: the redelivered report was only dropped, and always deleting on a drop would delete a newer report after a reconnect. (2) Two normalizers could race: a slow one's undo (`delete_source`) removed a newer report the other had applied, so the docs required exactly one normalizer.
Decisions:
1. **The generation is a column on `sync_states`** (`generation INTEGER NOT NULL DEFAULT 0`), stamped on every row the report sink writes. It is not part of `SyncState` (the model and the JSON in `state` are unchanged, so no existing test or reader sees a new field); `SyncStateStore.put` is unchanged too, and when it replaces an existing row it keeps that row's number (a writer that knows nothing of generations, such as single mode, must not reset it; a new row gets 0). `storage/sqlite_states.ensure_state_schema` creates the table, or, if the column is missing, `ALTER TABLE ... ADD COLUMN` at startup (SQLite and Postgres; a loser of a concurrent ALTER re-checks and carries on). Rows that existed before the column are stamped with the source's current generation, not 0: 0074's disconnect purges its rows, so a surviving row belongs to the current generation, and stamping 0 would have made the first stale drop after the upgrade delete valid data. A database without `source_generations` yet (single mode) has no bumps, so 0 is right. On SQLite the ALTER and the stamp are one transaction (an explicit `BEGIN`, because pysqlite does not open one before DDL), so an interrupted or failed stamp leaves the table as it was and the next start tries again; a stamp error is raised, not swallowed (`test_state_generation_column.py`).
2. **The state row is the generation marker for the source's events too.** Events have no generation column. `apply` writes a source's events and state in one transaction, so the state row's number says which generation the events were written under. An events-only leftover (no state row) cannot be told from current rows and is left alone; the transaction makes it impossible for the sink to create one.
3. **`ReportSink` port** (`core/ports.py`), implemented by `storage/sqlite_sink.SqliteReportSink` over one engine (events, `sync_states` and `source_generations` are in one database, the one `DATABASE_URL`). `apply(generation, window, events | None, state)` does, in one transaction: lock the source's generation row and read it; `current != generation` is `not_current` and nothing is written; a state row of an older generation is leftover from an unfinished purge, so the source's events and state are deleted first; `state.at` before the stored state's is `older` and nothing is written (this check used to be a separate read and is now race-free too); otherwise replace the events in the window (`EventStore.replace` rules; a foreign event is a `ValueError` that rolls everything back), store the state with the generation, and return `applied`. `purge_stale(source)` (same lock) deletes the source's events and state if the state row's generation is below the current one, and returns whether it deleted anything.
4. **The lock** is `lock_generation`: `INSERT ... ON CONFLICT DO NOTHING` of the row at 0 (so there is always a row; 0 and "no row" mean the same to `current`), then `UPDATE ... SET generation = generation RETURNING generation`. On Postgres that holds the row until commit, so a disconnect's `bump` waits for an apply in flight and two normalizers take turns per source; on SQLite the first write statement takes the database's write lock. A bump that commits first is seen by the check; one that waits happens after the commit, and its purge removes the write. The check after the write is kept as a backstop for a backend or a moment where that does not hold.
5. **The normalizer**: new optional keyword `sink`. With a sink: `apply`, then `not_current` is acked and dropped after `purge_stale` (idempotent: a redelivered drop finds nothing below the current generation, and never touches a newer connection's rows); `older` is acked; `applied` is followed by the old second check through `GenerationStore`, and if the number moved the normalizer calls `purge_stale`, which deletes only rows below the current generation. So a crash between the write and the check is cleaned up by the redelivery, and a slow normalizer's undo cannot delete a newer report: both open questions are closed for the sink path. Without a sink the normalizer behaves exactly as in 0074 (separate stores, undo by `delete_source`); only a `Normalizer` built by hand in a test or tool gets that. `workers/__main__._run_normalizer` always passes a sink, so every deployed normalizer is on the new path.
6. **"Exactly one normalizer" is removed** from `docs/distributed-mode.md`. `test_normalizer_atomic.py` runs the race that proved it necessary (a slow normalizer holds a generation-0 report while the user disconnects and reconnects and a second normalizer applies the new fetch; it then finishes, both when it drops the report and when its own write was already in) and the newer data survives; with the 0074 undo substituted into `purge_stale` those tests fail. The restriction stays only for a hand-built `Normalizer` without a sink, which the compose stack never starts.
7. **Tests** (new files only): `test_state_generation_column.py` (fresh database, old-schema database with a row, stamping from `source_generations`, idempotent setup, the store factory on an old SQLite file), `test_report_sink.py` (every rule above; a threaded race of applies against a disconnect), `test_normalizer_atomic.py` (crash between the write and the check then redelivery leaves the source empty, on the in-process stream and on Redis behind `CC_TEST_REDIS_URL`; the redelivered drop is a no-op and leaves a newer connection alone; the slow-normalizer races). `test_chaos_disconnect_sink.py` repeats the three scenarios of `test_chaos_disconnect.py` (worker killed mid-fetch, duplicate report, reconnect) over the SQL stores with a sink-backed normalizer, in-process and on Redis, because the 3e chaos tests build the normalizer without a sink and so never ran the deployed path (round-2 review). `sink_support.py` runs the SQL tests on Postgres too when `CC_TEST_POSTGRES_URL` is set. No existing test or fake changed: the in-memory stores in `worker_support.py` and `fakes.py` still serve the old path.
Alternative: (a) A generation column on `events` as well: a second persisted-table change and a migration of a large table, and not needed while the state row and the events are written together. (b) Put `generation` in `SyncState`: every reader and fake would see a new field for something only the sink needs. (c) Always delete a source's rows on a drop: deletes a newer connection's data after a reconnect. (d) A `SELECT ... FOR UPDATE` on the generation row only: it needs the row to exist, and SQLite ignores it, so the insert-then-no-op-update does both. (e) Keep the one-normalizer rule and only add the cleanup: the race it guards against is real only on the old path, and the lock makes the rule unnecessary. (f) Pass the sink to `Normalizer` instead of `events`/`states`: breaks every existing test that builds one.
Reason: a disconnect must be final even when a process dies at the worst moment, and more than one normalizer must be safe. Tagging the rows with the generation makes the cleanup exact (delete what is older, keep what is current) and idempotent, and one transaction removes most of the window the second check had to cover.
Open questions: none that need the owner. The reviewer raised two judgement calls, decided here. (A) Stamping pre-upgrade rows with the current generation assumes a surviving row belongs to it. That is false for exactly the 0074 leftover (a normalizer that died between its write and its check, before this upgrade): the stamp makes that one row permanent. Storage cannot tell it from a valid row, and a cleanup would need the secret store (the composition root). Accepted: the window that creates such a row is narrow, and it needs a pre-upgrade crash; to clear one by hand, disconnect and reconnect the source (the reconnect's first apply also clears events inside its window; the disconnect's unconditional delete clears the rest). (B) `QueuedSyncService.purge` (3e) still deletes the source's events and state unconditionally after its bump, outside the lock. If the user reconnects and a normalizer applies a new-generation report inside the few milliseconds between those statements, the new data is deleted (or, with the two deletes interleaved, events remain with no state row); the next scheduled sync restores it. Making it generation-aware means `purge_stale` instead of the deletes, which would leave events that have no state row (data from before 0075) behind on a disconnect, and a new constructor argument for `QueuedSyncService` that the existing test helpers do not pass. Left as it is; revisit when `QueuedSyncService` takes a `ReportSink`. Accepted: (1) a source that has never had an apply gets a `source_generations` row at 0 from the first apply; harmless, because `current` and `bump` treat it like no row. (2) `lock_generation` picks the insert dialect by name and knows SQLite and Postgres only. (3) The sink reads and writes `sync_states` rows with a synchronous call in `asyncio.to_thread`, like the other stores; a pool of threads could apply two reports of different sources at once, which is fine because the lock is per source.
Where: `core/ports.py` (`ReportSink`, `ApplyOutcome`), `storage/sqlite_sink.py`, `storage/sqlite_states.py` (column, migration, session helpers), `storage/sqlite_generations.py` (`lock_generation`), `storage/sqlite.py` (`replace_events`, `delete_source_events`: the store's own methods now call them), `workers/normalizer.py`, `workers/__main__.py`; tests above.
Not verified: Postgres (a local Postgres cannot start in this sandbox: SysV shared memory is blocked) and Redis (none installed): `test_state_generation_column.py` and `test_report_sink.py` run on Postgres with `CC_TEST_POSTGRES_URL=postgresql+psycopg://...` (a schema per test is created and dropped), the Redis cases of `test_normalizer_atomic.py` and `test_chaos_disconnect_sink.py` with `CC_TEST_REDIS_URL` (`docs/distributed-mode.md`). The SQLite and in-process cases pass. The Postgres row-lock behaviour (a `bump` waiting for an apply) is argued from the SQL, not run.
Supersedes: open questions 1 and 2 of 0074 and the "exactly one normalizer" known gap of `docs/distributed-mode.md`.
Revisit when: `QueuedSyncService.purge` can use the sink (accepted risk B); events need their own generation (a source's events written by something other than the sink); more than one database is used for events and states (the sink needs one engine); a database other than SQLite and Postgres is supported; the old normalizer path is no longer needed by any test, so the optional keywords can become required.
