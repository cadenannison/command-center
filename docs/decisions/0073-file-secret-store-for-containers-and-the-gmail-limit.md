# 0073. A file-backed SecretStore for containers, and Gmail's interactive sign-in

Status: accepted

Context: Task 3b. Rule 5 puts secrets in the OS keychain through `keyring`. A Linux container has no keychain, so the api and workers could not read or write a credential. Jobs and reports never carry credentials (0071); every process reads them from the `SecretStore`.
Decisions:
1. **`FileSecretStore(directory)`** implements `SecretStore` over `secrets.json` (`{user: {source: {key: value}}}`) in the data directory. The directory is created 0700 and the file is written 0600 by a temporary file and atomic rename; the store refuses to read a file that has group or other permission bits (the error says to `chmod 600`) and a corrupt file raises `SecretStoreError` without echoing its content. A `flock` on `secrets.json.lock`, plus a thread lock, serialises writers across processes (api and workers share the volume).
2. **Chosen by `CC_SECRET_BACKEND=file`**; `keyring` stays the default. `build_secret_store(backend, data_dir)` is the one place that chooses. The settings API stays write-only (`set` + last4) with either backend, and nothing secret is logged.
3. **The file backend is a deliberate step down** from the keychain: the secret sits in a 0600 file on a Docker volume, readable by anyone who can read that volume. It is for the distributed deployment only; the compose file keeps the volume private to the stack and `docs/distributed-mode.md` says not to use it on a shared host.
4. **Gmail's interactive sign-in cannot run in a container.** The adapter uses `InstalledAppFlow.run_local_server`, which opens a browser on the same machine and listens on a loopback port for Google's redirect. In a container there is no browser and the redirect cannot reach the published port. The workaround, documented in `docs/distributed-mode.md`: connect Gmail once in a single-process Command Center on a machine with a browser (with `CC_SECRET_BACKEND=file` and the same `CC_DATA_DIR` layout, or copy the `gmail` entry), then mount that `secrets.json` into the stack. The refresh token is long-lived but expires every 7 days while the consent screen is in Testing (0003), so the sign-in has to be repeated and the file replaced weekly. Other sources (Canvas token, Apple CalDAV, LearningSuite, weather) connect through the Settings page in the container as normal.
Alternative: (a) Add a device-code or out-of-band Gmail flow: a new adapter flow and a different Google client type, beyond this card. (b) Pass credentials as environment variables: they end up in `docker inspect` and process listings. (c) Docker secrets: read-only, so the settings page could not write them, and it still needs a first value. (d) Encrypt the file with a key from the environment: the key would sit next to the file, so it adds ceremony, not protection.
Reason: a container needs a writable store the settings page can use; the file keeps the same interface and the same write-only API.
Where: `adapters/file_secret_store.py`, `adapters/secret_backend.py`, `config.py` (`secret_backend`), `app.py`; tests `test_file_secret_store.py`, `test_config_distributed.py`.
Revisit when: Gmail gets a flow that works without a local browser; a real secrets manager is available in the target environment; the stack runs on a host others can read.
