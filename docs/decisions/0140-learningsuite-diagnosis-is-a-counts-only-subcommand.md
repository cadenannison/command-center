# 0140. `command-center diagnose learningsuite` prints counts, categories and dates only

Status: accepted

Context: Task L1: LearningSuite connects but a sync returns 0 items, and nothing says why (feeds outside the window, empty calendars, VTODO-only feeds, undated entries, a login page instead of a feed). The feed URLs are secrets (0005) and event titles are personal data, so the person running the diagnosis must be able to paste the whole output.
Decision:
1. `command-center diagnose learningsuite` (argv dispatch in `main` of `src/command_center/app.py`; no argument still serves) reads the stored URLs through the normal secret store (`build_secret_store`), downloads each feed once, and prints per feed: HTTP status class, content-type kind (calendar, html, text, json, other, missing), byte size, VEVENT and VTODO counts, how many have a start or due, the earliest and latest start or due as dates, and the VEVENT buckets inside / before / after the window, undated, cancelled, dropped (recurrence rules that could not be expanded). One `Conclusion:` line ends the output. Failures are fixed phrases, never an exception's text.
2. The window is the sync's own (`horizon_window` of now in UTC, as `SyncService` builds it: 14 days back, 60 ahead, end excluded), and the output says so.
3. VEVENTs are grouped by UID (a recurring item and its RECURRENCE-ID overrides) and each group is run through `events_in_window` with the feed's VTIMEZONEs. That is the adapter's own keep-rule, so a count follows what a sync keeps; every VEVENT of a group is counted under the group's bucket (before/after use the group's earliest start). One bad recurrence rule marks only its group "dropped", but a real sync raises `FatalError` for the whole feed and keeps nothing, so the conclusion puts "dropped" before every other answer. "dropped" covers any expansion `ValueError`, not only a recurrence rule. A VEVENT without a UID is its own group. Known difference: a sync expands the whole feed at once; a UID shared by unrelated items would be judged as one group.
4. VTODO are counted and dated (due, else start) but never bucketed with events: the adapter reads VEVENT only (0030), so a VTODO-only feed gets its own conclusion ("the sync reads VEVENT only, so it returns 0").
5. `ical_feed.check_feed_url`, `read_feed_capped`, `feed_urls` and `ical_events.localise` lost their leading underscore: the diagnosis reuses them, and a second copy of the SSRF check or the size cap could drift.
Alternative: A script under `scripts/` (not on the installed command, and the composition root is the only place that builds the secret store); a settings-page button (the web layer is being edited elsewhere, and a page adds an HTTP surface for something that reads secrets); classifying the whole calendar once and running each VEVENT alone (an override moved or cancelled would still leave its master "inside"; found by the reviewer) or mapping events back to components by UID (needs the adapter's private title fallback).
Reason: A person without a debugger can paste the output to the project manager; it exposes only what a count can. Reusing the adapter's own rule keeps the diagnosis honest.
Where: `src/command_center/adapters/ical_diagnose.py` (download and per-item classification), `ical_diagnose_report.py` (the report, the conclusion, the text), `diagnose_learningsuite` and `run_command` in `src/command_center/app.py`; tests `tests/test_ical_diagnose.py`, `tests/test_app_diagnose.py`; `docs/contracts/adapters.md`, `docs/first-run.md`.
Revisit when: Another source needs the same kind of diagnosis (then lift the argv dispatch into a small registry), or the card is allowed to carry adapter-supplied text (0141).
