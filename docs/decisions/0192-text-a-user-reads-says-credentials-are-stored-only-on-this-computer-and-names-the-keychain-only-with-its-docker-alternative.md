# 0192. Text a user reads says credentials are stored only on this computer, and names the keychain only with its Docker alternative

Status: accepted

Context: The Gmail card said pasted credentials are "stored in your computer's keychain" (decision 0190, amended). The project manager pointed out that this is false when the app runs under Docker, where `CC_SECRET_BACKEND=file` keeps credentials in a 0600 file on the data volume because a container has no OS keychain (decision 0073). A search found the same always-the-keychain claim in the Settings page intro, the chat key how-to, README, SECURITY.md and several docs.
Decision: Anything a user reads states where credentials live in words that are true in both modes: "stored only on this computer", and where the detail helps, "(in the OS keychain, or in a protected file when running under Docker)". The Settings page intro (`web/templates/settings.html`) carries the long form. The chat key how-to says "It is kept only on this computer". README, SECURITY.md, `docs/sources.md`, `docs/first-run.md`, `docs/runbook.md` and the storage contract's "never stores secrets" line were reworded the same way; the storage contract now says "the secret store". `tests/test_secret_storage_wording.py` fails if the Settings page, a how-to or one of those documents says a credential is "in the keychain" without the file alternative. Left alone because they describe the backends, not where a user's values are: the secret store, adapters and core contracts, `docs/distributed-mode.md`, decision records, module docstrings and the generated module index. Also left, and for the project manager to decide: AGENTS.md rule 5 and `docs/standards.md` ("Secrets: OS keychain through the keyring adapter"), which are the repo's own rules and describe the default adapter.
Alternative: Name only the keychain and add a Docker footnote (rejected: most readers would stop at the first claim). Say "in a secure place" (rejected: it says nothing a person can act on). Pick the wording at runtime from `CC_SECRET_BACKEND` (rejected: the page would then reveal configuration for little gain, and one sentence true in both modes is enough).
Reason: A privacy statement that is wrong in one deployment is worse than a vaguer one that is right in all.
Consequences: The page no longer tells a Mac user "keychain" unprompted except in the parenthesis on Settings. The wording guard is a regex over named files, so a new document must be added to its list. A new place that states the keychain flatly is caught only if it is in that list or on the Settings page or a how-to.
Where: `src/command_center/web/templates/settings.html`, `src/command_center/web/howto.py` (chat), `README.md`, `SECURITY.md`, `docs/sources.md`, `docs/first-run.md`, `docs/runbook.md`, `docs/contracts/storage.md`, `docs/contracts/web.md`; `tests/test_secret_storage_wording.py`.
Revisit when: A third secret backend is added, the file backend is removed, or AGENTS.md rule 5 is reworded.
