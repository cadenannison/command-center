# 0074. Per-source generation numbers, one shared sync state for both modes, and a connect that only enqueues

Status: accepted; open questions 1 and 2 resolved by 0075

Context: Task 3e, closing the gaps 0070 and 0071 left in distributed mode. The api read sync state from its own memory (so a worker's `reconnect` or `error` that the normalizer stored was never shown), connecting a source ran a sync inside the api (which could race a report fetched before the connect, 0071 item 5), and disconnecting did not stop work already in flight: a report published after the disconnect, or a redelivered one, put the source's events and state back.
Decisions:
1. **`GenerationStore` port** (`core/ports.py`): `current(source)` and `bump(source)`, both synchronous like the other stores, with `user_id="local"` keyword. `storage/sqlite_generations.py` implements it over SQLAlchemy (SQLite and Postgres): table `source_generations(user_id, source, generation)`. `bump` is one `UPDATE ... SET generation = generation + 1 ... RETURNING`, so concurrent bumps from several processes never return the same number; the first bump inserts the row and the loser of that race updates the winner's row. The row is never deleted, so purging a source's state cannot reset its counter.
2. **`Job.generation` and `SyncReport.generation`** (int, at least 0, default 0). The default keeps a job already sitting in Redis, and every existing test, valid. `SyncEnqueuer` (new keyword `generations`) stamps `current(source)` when it publishes, reading it at publish time; the worker copies it from the job into every report it makes (`ok`, `reconnect`, `error`).
3. **The normalizer drops a stale report and undoes a racing one.** Before applying, `current(source) > report.generation` means the source was disconnected after the job was queued: ack and drop, write nothing. After the writes it checks again; if the number moved while it was applying (the disconnect's purge may have run before its writes), it deletes the source's events and state, then acks. The disconnect bumps first and purges second, so the second check always sees a bump whose purge could have missed the writes. A redelivered report has the same old number and is dropped the same way. The new keyword `generations` is optional (`None` applies every report) only because `tests/worker_support.make_normalizer`, which existing tests use, builds a `Normalizer` without it and the card says tests are new-only; every composition root passes it (`workers/__main__.py`), and `test_normalizer_generation.py` and `test_chaos_disconnect.py` build it with one.
4. **One sync state, written by whoever syncs, read by the api in both modes.** `SyncService` takes `states: SyncStateStore | None` (`app.py` always passes one) and writes every state it remembers to it; `state()` answers from memory first, then from the store, so the last result survives a restart; `forget`/`purge` and a sync that finishes after a disconnect delete the stored row too. A store error is logged by exception class and ignored: the sync's own result matters more, and the memory copy still answers. The write is a small upsert done inline in `_remember` (a sync method called from many places); moving it to `to_thread` would turn `_remember` async in every branch, which I judged not worth it for a few hundred bytes on SQLite. `SettingsService._source_settings` reads `state` through `asyncio.to_thread`, which is where the distributed api's database read runs. Messages are unchanged: `safe_message`, redacted and at most 200 characters, before they are stored.
5. **`SyncControl` Protocol and `QueuedSyncService`** (`services/sync_control.py`, `services/queued_sync.py`). `Container.sync`, `SettingsService` and `SyncScheduler` now depend on the Protocol. In distributed mode `app.build_container` builds a `QueuedSyncService` over one Redis queue per source (the prefix function moved to `adapters/queue_redis.source_queue_prefix` so api, scheduler and workers share it; `workers/__main__.source_prefix` still exists and delegates), the shared stores, and a `SyncEnqueuer`. `Container.close` (new, optional) closes those Redis clients; the lifespan awaits it at shutdown.
6. **Connect validates only, then the route's background task queues one job.** `SettingsService.connect` is unchanged: validate, store, return `syncing`. The routes still call `container.sync.sync(source)` in a background task; with `QueuedSyncService` that publishes a job (generation stamped) and fetches nothing. So no sync runs in the api in distributed mode and the connect-time race of 0071 item 5 is gone. The card says connect "validates only and then enqueues"; the enqueue happens in the route's background task rather than inside `connect`, because `connect` has no queue and the routes already own that follow-up for both modes.
7. **The api stores no "syncing" row in distributed mode.** `QueuedSyncService.mark_syncing`, `record_error` and `error_state` return a state stamped with the api's clock and do not store it. The normalizer drops a report older than the stored state; the api's clock and a worker's clock are different machines, and a stored api row slightly ahead of the worker's `at` would make the normalizer drop the first real result. Consequence: after a connect, Settings shows no state until the first report is applied (the connect response itself says `syncing`).
8. **Disconnect.** `QueuedSyncService.purge(source)`: bump the generation, then `delete_source`, then `SyncStateStore.delete`. Order matters (item 3). Single mode keeps its in-process generation (`_forgotten`) for the sync running in this process; it does not bump the persisted number because no jobs exist there.
9. **`POST /v1/sync` in distributed mode** queues a job for every connected source and returns each as `syncing` (a source not queued is returned as last recorded, and left out if nothing was recorded). The schema is unchanged; the route docstrings (OpenAPI descriptions) for PUT, DELETE and POST were extended, so `docs/generated/openapi.json` changed in descriptions only (`gen:build`, `gen:check` clean). Single mode behaves as before.
10. **Failure to queue.** If the queue or the generation read fails, `QueuedSyncService.sync` logs the exception class (never the message: a Redis URL may hold a password) and returns an `error` state, "Could not queue the sync; it will be retried at the next scheduled round". Nothing is retried in the api.
Alternative: (a) A generation column on `sync_states`: purging the state would reset it, which is exactly when it must not go back to 0. (b) A timestamp ("disconnected at") instead of a counter: compares clocks of different machines, the thing item 7 avoids. (c) The worker reads the generation and refuses stale jobs: saves a fetch but is not enough alone (the report can still be late), so the normalizer's check is needed anyway; the worker check can be added later. (d) A Redis key for the generation: not durable across a Redis loss and Postgres already holds the other shared state. (e) Enqueue inside `SettingsService.connect`: the service would need the queue and would run on the request path (a failing queue would then fail the connect). (f) Persist a `syncing` row from the api: see item 7. (g) Make `generations` required on `Normalizer`: correct, but needs a change to a test helper the card did not allow.
Reason: a disconnect must be final. With a counter that every job and report carries and a second check after the write, a disconnect that lands before, during or after a normal apply leaves no events or state behind, and the api shows what the workers actually recorded. Two cases are not closed (Open questions below).
Open questions (the reviewer found them; they need the owner's decision): (1) a normalizer that dies or loses its database between its write and its second check leaves the write behind, because the redelivery only drops. The fix is to store the generation with the rows (a column on `sync_states`, a permanent identifier) and delete anything below the current number when dropping; recommended, but it changes a persisted table and `SyncState`. Alternative: write events and state in one transaction tagged with the generation. Accepting the gap is the third option. (2) Two normalizers can race: a slow one's undo deletes a newer report. Latent because compose runs one; the same generation-tagged rows fix it, or the docs require exactly one normalizer (done).
Also found and fixed: the scheduler read credentials before the generation, so a disconnect in between queued a job with the new number and the normalizer stored a `reconnect` row (it now reads the generation first); the generation store is now closed by the api and by the normalizer and scheduler roles. Accepted and recorded: the connect route's background enqueue after a quick disconnect behaves as in single mode (item 6); single-mode `purge` does not bump the stored number (item 8, revisit when modes are switched back and forth); a single-mode restart can show a stored `syncing` row until the startup sync replaces it; jobs and reports gained a field under `extra="forbid"`, so all roles must ship from one image.

Supersedes: the "known gap" parts of 0070 (the api reads in-memory state, connect syncs in the api, disconnect does not purge shared state or in-flight reports) and item 5 of 0071.
Revisit when: a worker should skip a stale job before fetching (decision 0074 alternative c); more than one user is served (the generation is per `user_id` already); scheduler jobs should be collapsed while a source is down; a state row for `syncing` is needed and the clocks are synchronised by one source.
