# 0057. Phone pairing, Host-based device auth and the menu-bar launcher

Status: accepted

Context: Task 3c (security-critical). A phone reaches the Mac through Tailscale Serve, which proxies to 127.0.0.1 but keeps the tailnet name in `Host`. The card fixed the token lifetimes, the hashing, the rate limit and the Host rule; the decisions below are the places it left open or where the layer rules forced a different shape.
Decisions:
1. **Where the code lives.** `Container` is in `services` and may not import `pairing` (pyproject), so `PairingService` is `services/pairing.py`, built on pure rules in `core/pairing.py` and `core/hosts.py` and two ports (`TokenSource`, `DeviceStore`). The `pairing/` package holds only `pairing/qr.py` (payload and SVG), which `web` imports. `api/auth.py` and `api/pairing_routes.py` hold the middleware and routes. Storage is `storage/sqlite_devices.py`, tokens come from `adapters/system_tokens.py` (`secrets.token_urlsafe`; core stays pure).
2. **Tokens.** Pairing token 16 bytes, refresh and access 32 bytes, all opaque; only SHA-256 hex is stored. A pairing token is single use through one atomic `DELETE ... RETURNING` that also checks expiry; only one is live at a time. Lookups on the read paths (`refresh_record`, `device_for_access`) go by digest and then compare with `hmac.compare_digest` (`hashes_match`). The atomic state changes match the digest inside SQL; a timing difference there reveals nothing usable because the attacker would need to control a 256-bit digest, and the compare is not the only barrier (the limiter is).
3. **Refresh rotation.** `POST /v1/pair/refresh` (a route the card did not name) swaps a refresh credential for a new pair. The superseded credential is kept, so presenting it again is recognised as reuse and deletes the device with all its credentials; it is logged at WARNING by device id only. It is an open path (no bearer needed) next to `/v1/pair` and `/v1/health`, because the caller's access token has expired by definition.
4. **Rate limit.** `FailureLimiter` (5 failures, then a 60 s lock), one for pairing and a separate one for refresh, in memory, behind a lock, **global rather than per client**: behind Serve every request comes from 127.0.0.1, so there is no client address to key on. The cost is that someone on the tailnet can lock the real phone out for 60 s at a time; the benefit is that guessing a 128-bit token stays hopeless. A locked response is 429 with `Retry-After`; every other refusal is the same 401 with one generic message, the reason code goes only to the log.
5. **Host decides.** `core.hosts.classify_request` gives LOOPBACK, REMOTE or REJECTED. Only `localhost` and `127.0.0.1` Hosts with **no proxy header** (`forwarded`, `x-forwarded-*`, `x-real-ip`, `via`, `tailscale-*`) are LOOPBACK. A loopback Host that carries a proxy header is REMOTE, because a tailnet peer can send `Host: localhost` and Serve forwards to 127.0.0.1; failing closed costs nothing for the browser, which sends none. Hosts in `CC_ALLOWED_HOSTS` are REMOTE and need `Authorization: Bearer <access token>` on every route except `/v1/pair`, `/v1/pair/refresh` and `/v1/health`. Any other Host is 400 (also for the middleware's own check, so DNS rebinding gets nothing). **Unverified:** that Tailscale Serve keeps the tailnet name in `Host` and adds identity headers was taken from the card and its documentation, not observed here; docs/mobile.md asks for a manual check, and if Serve rewrote `Host` to a loopback name without a proxy header, remote requests would be served with no token. `Settings.allowed_hosts` accepts only plain lowercase hostnames (no scheme, port, path, wildcard, or loopback name) so the list cannot widen the rule by accident.
6. **Minting a code is a POST.** The card says the `/pair` page shows the QR and token. `GET /pair` shows the page; `POST /pair/code` (CSRF-protected like every web write, loopback only) mints the token. A GET that mints a credential would let any page that can make the browser fetch it (an image tag, a prefetch) burn pairing tokens, and would put live tokens in history and caches. The token is in the response body and in the QR JSON (`{"v":1,"url":...,"token":...}`), never in a URL.
7. **No `user_id` on `DeviceStore`.** Devices belong to this Mac, not to a user of the events table; the single-user assumption of the rest of the app (`user_id="local"`) is not spread into a new table.
8. **API contract.** `POST /v1/pair`, `POST /v1/pair/refresh`, `GET /v1/devices`, `DELETE /v1/devices/{id}` are added and every protected route declares the `DeviceToken` bearer scheme in OpenAPI (documentation only; the middleware enforces). `api.md` said no response carries a credential; the two pairing responses are the deliberate exception (they are `Cache-Control: no-store`, `repr=False` in the models). This is an additive change for the mobile repo. `GET /v1/devices` and `DELETE` need a token for a remote caller but not for the web UI.
9. **Existing `/v1` writes have no CSRF token.** The new pairing writes are JSON-only (a form or `text/plain` post is 422) and there is no CORS, so a cross-origin page cannot send them with credentials; the web UI's writes keep their `X-CSRF-Token`. The older `/v1` PUT/DELETE/POST routes rely on the same two facts plus the Host check and were not changed; see the follow-up below.
10. **Menu bar.** `desktop/main.py` is the composition root; `adapters/menubar_rumps.py` is a thin shell with no decisions and is the only `rumps` importer. Title wording, the plist and the server command are rumps-free modules (`menu_title`, `launch_agent`, `server_process`, `events_client`) so they run on Linux CI. The app does not share the server's container: it starts `uvicorn --factory command_center.app:create_app` on 127.0.0.1 as a child (unless `/v1/health` already answers; it then stops only what it started) and polls `GET /v1/events` every 60 s over loopback HTTP (a client that refuses non-loopback URLs, 5 s timeout). The LaunchAgent plist is written atomically (mode 0644, no environment block) but not loaded with `launchctl`; it takes effect at the next login.
11. **Wire names.** The pairing request field is `pairing_token`, not `token`: the existing schema test (`test_no_response_schema_has_a_field_that_could_carry_a_credential`) forbids a property named `token` outside `ConnectRequest`, and the longer name is also clearer next to `refresh_token` and `access_token`. The QR JSON keeps the key `token`.
Test edit (allowed by the project manager): `tests/test_smoke.py` only. The `desktop.main` case of `test_unbuilt_composition_roots_fail_loudly` called `main()` and expected `NotImplementedError`, which the card made obsolete; it would also have started a server and the menu bar on a Mac. The test now covers only `workers.__main__`, and a new `test_the_menu_bar_root_imports_without_running` imports `desktop.main` and never calls `main()`. `test_app_wiring` (decision 0058) is not touched and still fails.
12. **Known limits, accepted until the human decides otherwise (review findings).** (a) A refresh whose response is lost leaves the phone holding a superseded credential; presenting it again counts as reuse and revokes the device, so the user pairs again. A grace window would weaken theft detection, so there is none; the phone app should store the new pair before it uses it and treat a failed refresh as "pair again". (b) The LaunchAgent has no environment block (so no secret or setting can leak into it) and launchd gives the app no `CC_*` variables, so the server it starts at login has no `CC_ALLOWED_HOSTS` and the tailnet name is refused until the app is started from a shell that has them. Recommended fix: a non-secret settings file read by `Settings`; not built here. (c) A paired phone is trusted like the web UI: it can reach every `/v1` route and the settings pages, including connecting or deleting sources and revoking other devices. Restricting a remote caller to read-only plus pairing is the likely next decision. (d) A crashed server is not restarted by the menu bar (a restart needs a cap and backoff); the title reads "CC offline" until the app is relaunched.
13. **Credential rows and revoked devices.** `device_for_access` joins `devices` and the refresh claim requires the device row, so credentials left by a rotation that raced a revocation on a database without serialised writers (Postgres) are inert. SQLite serialises writers.
Alternative: (a) `PairingService` in `pairing/` with the container knowing it (needs a pyproject change to the layer contract). (b) Per-client rate limits via `X-Forwarded-For` (Serve's headers cannot be trusted from the tailnet, and the request is loopback anyway). (c) Trust a loopback Host unconditionally (a tailnet peer could then send `Host: localhost`). (d) Mint the token on `GET /pair` as the card words it. (e) A JWT or signed token (card forbids; opaque and revocable is simpler). (f) The menu-bar app sharing the container in process (couples the GUI thread to the server and needs adapters in two roots). (g) `launchctl bootstrap` from the app (more to get wrong; deferred).
Reason: each choice keeps the card's guarantees (single use, short life, hashed storage, revocable, fail closed) while fitting the import rules and the fact that Serve hides the client address.
Where: `core/pairing.py`, `core/hosts.py`, `core/ports.py`, `services/pairing.py`, `services/errors.py`, `storage/sqlite_devices.py`, `adapters/system_tokens.py`, `adapters/menubar_rumps.py`, `api/auth.py`, `api/pairing_routes.py`, `api/factory.py`, `pairing/qr.py`, `web/pair_routes.py`, `config.py` (`allowed_hosts`), `app.py` (`build_pairing`), `desktop/*`; tests `test_core_pairing.py`, `test_core_hosts.py`, `test_pairing_service.py`, `test_sqlite_device_store.py`, `test_auth.py`, `test_pair_api.py`, `test_web_pair.py`, `test_app_pairing.py`, `test_desktop_*.py`.
Revisit when: any limit in item 12 is decided; Serve's `Host` behaviour is checked on a real tailnet (item 5); the global lock proves annoying (move to the Tailscale identity headers once they are verified); the older `/v1` writes get a CSRF or content-type check; the app needs `launchctl` loading or a second user.
