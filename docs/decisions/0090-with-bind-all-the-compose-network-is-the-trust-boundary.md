# 0090. With `CC_BIND_ALL` set, the compose network is the trust boundary

Status: accepted; qualifies 0072

Context: Task 4d, closing the last open decision of 0085. 0072 made `CC_BIND_ALL=1` the one way to listen beyond loopback and said every published port is `127.0.0.1:<port>:<port>`, "so the host's loopback is still the only reachable address". That holds for the host. It does not hold inside the compose network: the api's auth middleware lets a request through with no token when its `Host` is loopback (`localhost`, `127.0.0.1`) and it carries no proxy headers (`api/auth.py`, `core.hosts`), and it never looks at the peer address. With the api listening on `0.0.0.0` in its container, any container on the compose network, redis and postgres included, can send `Host: 127.0.0.1` and is treated as the local user.
Decision: document it as the boundary; change no code. A peer-address check is not an option: Docker delivers traffic for a published port from the bridge gateway, so the peer of a legitimate browser request is not loopback either, and a check that rejected non-loopback peers would reject the web UI. The statement, in `docs/distributed-mode.md` (Trust boundary) and the README security model:
- the compose network is trusted: only services of this repo and the official images in `docker-compose.yml` are on it, and nothing else may be attached;
- only the api publishes a port, and only on `127.0.0.1` (`tests/test_compose_file.py` checks only that each quoted `host:port:port` mapping starts with `127.0.0.1:`; that only the api publishes one is a rule for whoever edits the file, not a tested guarantee); the phone arrives through Tailscale Serve and is held to a device token;
- the stack is for a single trusted host: whoever can run a container there or join the network already holds the credentials volume and the database.
0072's Status line carries a pointer to this record; its text is otherwise unchanged (AGENTS.md lets an old record change only on its Status and Sources lines).
Alternative: (a) Require a token for every request in distributed mode, loopback Host included: breaks the web UI's no-login use and the smoke scripts, and the token would have to live in the browser. (b) Separate networks for the api and for redis/postgres: the api needs redis and postgres, so it would join both, and every service on the network it shares with a client could still reach it. (c) Check the peer against the gateway address: it is a guess about Docker's addressing that differs by platform and would be unverifiable here (no Docker daemon).
Reason: the honest description of the threat model is cheaper and safer than a check that cannot work; the risk is bounded by what is on the network, which this repo controls.
Where: `docs/distributed-mode.md` (Trust boundary, Known gaps), `README.md` (security model item 1), `docs/decisions/0072-...md` (Status line).
Not verified: the behaviour was argued from the code and Docker's documented networking, not observed; this sandbox has no Docker daemon.
Revisit when: any service that is not this repo's is attached to the compose network; the api is put behind a reverse proxy in its own network (then it could listen on that interface only); a multi-user or shared-host deployment is wanted.
