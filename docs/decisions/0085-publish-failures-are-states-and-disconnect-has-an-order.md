# 0085. A failed publish is an error state per source, and a disconnect cancels, then deletes secrets, then purges

Status: accepted; its open decisions are answered by 0086 (the second bump), 0087 (the script rename and findings), 0088 (the shared `until_fetching`), 0089 (token-shaped strings in `redact`) and 0090 (the bind-all trust boundary)

Context: Task 4c. Decision 0084 listed two things it did not decide: `POST /v1/sync` hid a dead Redis (the failed source was just missing from the answer, while `docs/distributed-mode.md` said an `error` state is shown), and `SettingsService.disconnect` deleted the secrets first, then bumped the generation and purged in one call, so a failure in the middle left no way to tell it had happened.
Decisions:
1. **`SyncEnqueuer.publish_outcome()`** returns `PublishOutcome(published, failed)`. `failed` holds the sources whose secret read or publish raised, and the connected ones whose generation read raised (a failed generation read is raised only after the credentials show the source is connected, so a down database does not make an unconnected source an error); each is logged by exception class only and the others still go out. `publish_connected()` stays and returns `outcome.published`, `publish_round()` its length. `QueuedSyncService.sync_all` returns `syncing` for a published source, an `error` state (`QUEUE_FAILED_MESSAGE`, the same text `sync` uses, not stored) for a failed one, and as before the recorded state for the rest. That read now goes through `state()`, so an unreadable database row for one source is "unknown" (0084) instead of failing the whole request. A source with no credentials is neither published nor failed.
2. **`SyncControl` gains `cancel(source)`; `purge` no longer bumps.** `QueuedSyncService.cancel` bumps the generation, `purge` deletes events and state, `SyncService.cancel` does nothing. `SettingsService.disconnect` runs `cancel`, then deletes the secrets, then `purge`. A failing `cancel` stops before anything is deleted and returns `SourceSettings` with the keys still stored and an `error` state `DISCONNECT_FAILED_MESSAGE`. A failing `purge` returns no keys and an `error` state `DISCONNECT_INCOMPLETE_MESSAGE`. An integration has no generation or rows, so it only deletes its secrets. Disconnecting again repeats all three steps and finishes the job, and so does the first report applied after a reconnect (it deletes rows of an older generation, 0075). Until one of those happens the stale state and events stay visible, because nothing is published for a source with no credentials; the incomplete message is shown in that one response only. The bump has already made the normalizer drop every report and job queued before it.
3. **Both failures are results, not exceptions, and the API shape does not change.** They use the existing `SourceSettings.sync` error state, a 200, and fixed message text. The web card already shows `result.sync.message` as a failed flash and its Delete button is always present, so retry needs nothing new. Logs carry the step and the exception class only, because a database error can echo the connection URL.
Alternative: (a) Change the return type of `publish_connected` to carry failures: it breaks `test_publish_connected_names_the_sources_it_queued` and tests may not be edited, so a second method was added. (b) A 5xx or a new response field for a failed disconnect: `openapi.json` is the contract of the mobile repo, so a new field or status is a breaking-change decision this card did not ask for. (c) Keep `purge` as bump plus deletes and add a flag: the order is the point, so the bump has to be callable on its own. (d) On a failed purge put the secrets back: they cannot be restored (the user asked for them to be deleted) and a retry is cheap.
Reason: a failure that looks like success is the worst outcome for a delete: the user believes the data is gone. Bumping first means the only failure that can leave anything running is one that also aborts the delete, and no failed step leaves the user without a message.
Where: `src/command_center/services/scheduler.py` (`SyncEnqueuer.publish_outcome`), `queued_sync.py`, `sync.py`, `sync_control.py`, `settings.py`; tests `tests/test_queued_sync_publish_failure.py`, `tests/test_settings_disconnect_order.py`; `docs/contracts/services.md`, `docs/contracts/api.md`, `docs/distributed-mode.md`.
Not done: `redact` removes email addresses and digit runs of six or more, nothing else, so an alphanumeric token such as `fake-secret-abc123` in a worker's message is not redacted by it (`tests/test_distributed_connect.py` now asserts the email and a long digit run, which are what `redact` promises). Credentials stay out of messages because no code path puts them in, not because `redact` finds them. Whether `safe_message` should also mask token-shaped strings is a design decision for the human.
Open decisions (not decided here; each needs the human):
- **A job can slip past the new order.** A sync published between the bump and the credential delete is stamped with the new generation, so its report is applied after the purge (or leaves a `reconnect` row). The old order (secrets, then bump) had no such window but could not abort cleanly. Recommended fix: bump again at the start of `purge`, which closes it. That ends a disconnect on generation 2, and `test_disconnect_purges_events_and_state_and_bumps_the_generation` (tests/test_distributed_connect.py:149) asserts exactly 1; the card allows edits to that file only for the redaction assertion, so it was not changed. Listed in docs/distributed-mode.md Known gaps.
- **A failed purge leaves stale data visible after a reload.** Persisting an "incomplete" marker (a state row, or an API field the mobile repo would see) is a design choice; today a retry or a reconnect cleans up.
- **Renaming `scripts/gen-decision-index` to `scripts/gen_decision_index.py` was not done.** The card says to update its test, but tests/test_gen_decision_index.py is an existing test, outside the two files the card allows editing, and loads the script by its current path; the rename alone fails it. Needs that file added to the allowance (or the card amended). The same file would also take the script findings below.
- **Script findings, not fixed because they change the script that test covers:** `scripts/gen-decision-index` reads "superseded by decision 0060" or "superseded in part by 0060" as having no replacement and reads only the first "supersedes" clause of a Status line, without error (no real record triggers either today); and three of its tests assert less than their names say (in-part from the supersedes side only, comma lists).
- **`until_fetching` in tests/test_chaos_distributed.py has no time limit** (decision 0080 says the hang is solved; only test_chaos_disconnect.py has the bound, and test_chaos_disconnect_sink.py has one without a failure message). Fixing it edits existing tests; a shared bounded helper in `tests/worker_support.py` would remove the three copies.
- **With `CC_BIND_ALL` set, the loopback Host exemption admits any peer on the compose network**, redis and postgres included (api/auth.py never checks the peer address). The README now says the opt-in exists for the container; whether to also check the peer address, or document the wider exemption in 0072, is a decision.
Revisit when: the stack runs against a real Redis (is `QUEUE_FAILED_MESSAGE` the right text for a failed secret read?), or the mobile repo wants a machine-readable "incomplete" flag.
