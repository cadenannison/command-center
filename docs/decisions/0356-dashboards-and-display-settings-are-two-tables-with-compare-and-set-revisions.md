# 0356. Dashboards and display settings are two tables with compare-and-set revisions

Status: accepted

Context: Task R2 persists dashboards and one row of display settings on SQLite and Postgres. Two browser tabs must not overwrite each other.
Decision: Table `dashboards(user_id, id, name, position, layout, revision, updated_at)`, primary key `(user_id, id)`, `layout` JSON text. Table `display_settings(user_id, settings, revision, updated_at)`, one row per user, `settings` JSON text of the fields in `DisplayInput`. A replace or delete is one `UPDATE/DELETE ... WHERE revision = :expected`; zero rows then means not found or a revision conflict, so no lock or read-modify-write is needed on either database. A dashboard starts at revision 1 and each replace adds 1. Display settings have revision 0 until first saved; the first save must send 0 and a second writer's insert hits the primary key and is a conflict. Reorder does not change revisions (it changes only `position`) and must name exactly the stored ids, so a stale tab gets a conflict instead of dropping a dashboard it never saw. At most 20 dashboards per user. A display row that no longer parses reads as the defaults at its revision, so the next save repairs it. Tables are created if missing, like the other stores; the display settings hold no AI provider setting and no secret, by the shape of `DisplayInput` (unknown keys are refused).
Alternative: Optimistic locking in the service with a read then a write (rejected: a race between them). A key-value row per setting in `app_settings` (rejected: no revision for the whole set, 500-character values). Bump every revision on reorder (rejected: it would make a harmless reorder fail a tab's unrelated layout save).
Reason: One atomic statement gives the same guarantee on both databases with the least code.
Consequences: The 20-dashboard cap is a check then an insert, not atomic: two simultaneous creates could both pass at 19 and leave 21 (and a repeated position, ordered by id). Accepted as a soft cap because the writes are loopback-only and single-user; if it happens, `PUT /v1/dashboards/order` (needs at most 20 ids) cannot succeed until one is deleted. A delete of an unknown id is 404 before any conflict is reported. The 20-dashboard cap is a judgement call and is cheap to change.
Where: `src/command_center/storage/sqlite_dashboards.py`; `tests/test_dashboard_store.py` (Postgres runs only with CC_TEST_POSTGRES_URL).
Revisit when: dashboards are shared between users, or a per-user cap other than 20 is wanted.
