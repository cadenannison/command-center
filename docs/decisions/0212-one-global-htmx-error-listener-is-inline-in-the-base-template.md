# 0212. One global htmx error listener shows the server's text in the row's flash area, inline in the base template

Status: accepted

Context: htmx 2 swaps no 4xx or 5xx reply by default, so editing a synced item (409), acting on a deleted item (404) or a failed CSRF check (403) left the page unchanged with no message.
Decision: A small listener for `htmx:responseError` on `document` reads the reply as JSON and shows `detail` (FastAPI's error shape) in the nearest `.flash` inside the clicked element's nearest `li`, `.card` or `.panel` (not `form`: a row's flash sits after its note and task forms, not inside them), adds `bad`, and opens the enclosing `<details>` so a flash inside a closed panel is seen. A reply that is not JSON with a string `detail` (a 422 list, HTML) shows "The server refused the request (<status>)." instead, so no raw body is ever shown. The text is set with `textContent`, never HTML. If the element has no flash area nothing changes. The script lives in `templates/_htmx_errors.js` and `base.html` includes it in an inline `<script>`, so the vendored `htmx.min.js` is not edited and `htmx.config` is unchanged. The failing replies themselves are unchanged and still not swapped.
Alternative: A static `/static/cc.js` loaded after htmx (cleaner, and cacheable). Rejected for now because `tests/test_web_pages.py::test_pages_load_nothing_from_outside` pins the page's `<script src>` list to exactly the vendored htmx file and this card did not allow editing that test. Also rejected: `htmx.config.responseHandling` with `swap: true` for 4xx (it would replace the row with the JSON body).
Reason: Inline needs no change to an existing test and no new served path. The listener is 30 lines and has no state.
Where: `src/command_center/web/templates/_htmx_errors.js`, `base.html`. Tests: `tests/test_web_error_handler.py` (every page declares the listener; every htmx control's nearest `li`, `.card` or `.panel` holds a flash area; the 409, 404 and 403 replies carry the fixed texts; the row has a flash area). The listener's DOM behaviour was checked with a stub in node, not in a real browser, and no test runs JavaScript.
Revisit when: A Content-Security-Policy is added (inline script would then need a nonce or a file), or `test_pages_load_nothing_from_outside` may list a second script. Then move it to `web/static/cc.js`.
