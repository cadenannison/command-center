# 0100. Which credential keys are secret is decided in one services module; plain values ride on `SourceSettings.values`

Status: accepted; the exposure to a paired phone is removed by 0106

Context: Task A1 says the settings status exposes the value of non-secret fields (Canvas base_url, iCloud username, weather latitude/longitude) and only set/last4 for secrets, and that the secret flag is marked per source in one place. Until now the flag was `Field.secret` in `web/sources.py`, which only decided the input type; the service and the API treated every key alike. The service layer cannot import `web`, and `core/` (where `SecretStatus` lives) is being edited by other sessions.
Decision: `services/credential_fields.py` holds `NON_SECRET_KEYS` (source to keys) and `is_secret(source, key)`. It is an allow-list of what may be shown back: a key, or a whole source, that is not listed is secret, so a new key is hidden until someone lists it. `web/sources.py` builds each `Field` with `secret=is_secret(...)`, so the form and the service cannot disagree (`test_every_form_field_is_secret_exactly_when_the_services_list_says_so`). `SettingsService.status()` reads the stored value of each non-secret key that is set into `SourceSettings.values: dict[str, str]` (default `{}`); secrets are never read for that. `keys` is unchanged: every key still reports `set` and `last4`. The cards prefill from `values`.
Alternative: Add a `value` to core's `SecretStatus` (a core change, and it would put a field that is null for secrets on every key); or keep the split in `web/sources.py` and filter in the route (the API and the mobile client would still get no plain values, and the service could not tell what it may return).
Reason: One allow-list in services is the smallest change that both layers can import. A separate `values` map keeps `SecretStatus` meaning "status, never a value" so a future key cannot leak through a field that is sometimes filled. The API change is additive (`openapi.json` is regenerated): existing mobile clients ignore an unknown property.
Where: `src/command_center/services/credential_fields.py`; `SourceSettings.values` in `services/models.py`; `SettingsService._plain_values` in `services/settings.py`; `Field`/`_field` in `web/sources.py`; `FieldView.value` in `web/cards.py`. Tests: `tests/test_settings_usability_service.py`, `tests/test_web_settings_usability.py`, `tests/test_api_settings_usability.py`. Existing tests changed with the project manager's approval: the two in `tests/test_web_settings.py` (`test_no_input_is_ever_prefilled` became `test_a_secret_input_is_never_prefilled` plus `test_a_non_secret_input_is_prefilled_with_the_stored_value`; `test_no_credential_value_appears_in_any_response` now counts only secret values as leaks), and the six exact-shape assertions that gained `"values": {}` (`tests/test_api.py` x2, `tests/test_gemini_key_entry.py` x2, `tests/test_json_only_writes.py`, `tests/test_app_wiring.py`).
Rule 5 and `.claude/rules/layers.md` say the settings API is write-only (status = set + last4). This change narrows that to secrets, as the project manager approved for Task A1: `GET /v1/settings` now returns the Apple ID (often an email address), the Canvas URL and the weather coordinates (an approximate home location). A paired phone may make that GET (decision 0060 limits a phone's writes, not its reads), so it receives them. If that is not wanted, strip `values` for token-authenticated requests in `api/policy.py` or the route; nothing else changes. AGENTS.md rule 5 has not been edited.
Revisit when: A source gains a key that is safe to show (list it in `NON_SECRET_KEYS`), or the mobile repo wants `values` typed per key.
