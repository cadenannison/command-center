# 0381. The Summary card is pinned above the grid, tiers by column count, and is fetched once per day per mount

Status: accepted

Context: Card U5 asks for the Summary (kind `summary`) in the dashboard. Decisions 0331 and 0350 and `docs/design/spec.md` (lines 27 and 51) make it a kind with no grid definition, "pinned above the grid, collapsible"; a layout item with that id is dropped on read. `GET /v1/summary?date=` (decisions 0037, 0053, 0112) is 404 `Summaries are off` by default, and otherwise 200 with `provider` `stored` (an earlier day, no date in the response), `template`, or the configured provider's name. `SummaryService.get` builds and stores the day's summary on the first request for a day, so a GET can call the AI provider; a `template` result is never stored, so the next GET calls the provider again.
Decision:
- The card is `SummaryCard` in `ui/src/features/dashboard/summary-card.tsx`, rendered by `dashboard-view.tsx` after the notices and before `DashboardGrid` (DOM order is visual order). It is a `section` labelled by its `h2`, visible in edit mode, and takes no focus. It is not a grid widget: no registry entry, no sanitizer entry, no layout item, no Python change, and `registry.test.ts` and `validate.test.ts` are untouched, which keeps them true (this is consistent with 0331 and 0350). `summary-placement.test.tsx` asserts it is outside the grid and before it.
- Tiers are the grid's column count (`columnsForWidth`, 4, 8 or 12), not the registry's width and height tiers, because the card has no registry entry or size row. 4 columns: headline and up to 3 priorities, no heads-up. 8: headline, up to 4 priorities, heads-up below. 12: headline, up to 5 priorities, heads-up side by side. "+N more" whenever priorities are cut. Collapsed shows the headline only (a fallback notice stays with it). Collapsed is component state, default expanded; persistence waits for the display-settings card.
- States: loading; off (the 404 only, "Summaries are off" and "They can be turned on in Settings.", no link because Settings is not built); error (any other failure, or a body that is not a summary) with fixed text and Retry; ready, with a notice for `stored` ("Showing an earlier summary", no date because the API gives none) or `template` ("Showing a basic summary"). A failed refresh keeps the summary on screen with a fixed notice and Retry. Server text is never shown. The 404 is told apart by `ApiError.kind` `not_found`.
- Fetching: because a GET can call the provider, `useSummary` sets `refetchOnWindowFocus` false, `refetchOnReconnect` false, `refetchInterval` false, `retry` false and `staleTime` 5 minutes. The key is `["summary", localDay]`, so there is one request per local day per mount; a day change at midnight asks once for the new day and keeps the old one on screen meanwhile (as 0379). Only the Retry button asks again. The date is the local calendar day of the clock parameter (`summaryDay(now)`).
- Untrusted text: the summary derives from feed and mail content. `parseSummary` copies only `summary.headline`, `priorities`, `heads_up` and `provider` (extra fields are dropped), at most 10 entries per list, removes control and bidirectional-override characters, collapses whitespace and clips every string to 200 characters. Strings render only as React text nodes: no HTML, no markdown, no auto-linking, no link elements.
Alternative: A grid widget (rejected: needs a new decision superseding 0331 and 0350, registry and Python changes, and layout-test edits). The default retry and focus refetch of the other widgets (rejected: each could pay for a provider call; a failed `template` summary would call the provider again on every focus). Polling (rejected for the same reason).
Reason: The spec and earlier decisions fix where the Summary lives; the fetch rules follow from what the service does on a GET.
Consequences: Existing page tests that answered every path with a dashboard list got a `/v1/summary` stub (tests: modify, listed in the task report). A response whose `provider` is `stored` after an earlier-day fallback carries no date, so the notice has none. The card's glow is the default (ice) one: Summary has no source color.
Where: `ui/src/features/dashboard/summary-model.ts`, `use-summary.ts`, `summary-card.tsx`, `dashboard-view.tsx`; tests `summary-*.test.ts(x)`, `ui/e2e/dashboard-summary.spec.ts`.
Revisit when: the display-settings card can persist collapse; the API adds a date for a stored summary or an error code for "off"; Settings exists (add the link).
