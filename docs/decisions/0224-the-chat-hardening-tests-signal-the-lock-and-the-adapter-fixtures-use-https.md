# 0224. The chat hardening tests signal the lock, and the adapter fixtures use https

Status: accepted

Context: The task card allows edits to `tests/test_chat_hardening.py` and `tests/test_chat_remote_policy.py`, and to existing tests that fail solely because of the new behaviour. (1) The lock re-check tests waited on one `asyncio.sleep(0)`, which passes whenever the second message happens to reach the lock in one loop turn. (2) With 0220, 18 cases in `tests/test_chat_adapters.py` failed only because their provider held a key and called `http://192.168.1.20`.
Decision: (1) `test_chat_hardening.py` replaces the service's lock with a `SignallingLock` that sets an event the moment a task finds it held, and the helper waits on that event (5 s guard so a missing signal fails instead of hanging). With the re-check removed from `ChatService.reply`, both lock tests fail (checked by hand on 2026-11-09, then restored). The delete test now also asserts the second DELETE of the same id is 404. `test_chat_remote_policy.py` splits the Mac's POST and GET into two tests: the POST asserts the reply text and a non-empty `conversation_id`, the GET asserts the preview holds the agenda title. (2) In `test_chat_adapters.py` `BASE` becomes `https://192.168.1.20:8080/v1`, so the key tests keep a key and keep their assertions; the two parametrized lookup tests (`..._are_not_looked_up`, `..._resolves_to_this_machine_or_lan_is_called`) pass `key=None`, because they assert the address check, not the header. No assertion was changed, deleted or weakened. The new key behaviour is tested in the new files.
Alternative: Read `asyncio.Lock`'s private waiter list or count loop turns (both depend on asyncio internals); give `ChatService` a test-only hook (production code for a test); default the `openai()` helper to no key (would make the "key never echoed" assertions vacuous).
Reason: The signal names the event the test is about, and the fixture edits are the least that keep every old assertion meaningful.
Where: `tests/test_chat_hardening.py`, `tests/test_chat_remote_policy.py`, `tests/test_chat_adapters.py` (`BASE`; `test_localhost_and_literal_addresses_are_not_looked_up`; `test_a_local_name_that_resolves_to_this_machine_or_lan_is_called`).
Revisit when: `ChatService` exposes a public way to observe a queued message.
