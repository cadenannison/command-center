# 0255. The IPv4 rule runs after the digit-group rule

Status: accepted; supersedes in part 0240 (the position of IPv4 in the rule order) and 0244 (IPv4 is matched inside a digit group only when the group is exactly an address)

Context: Decision 0240 put IPv4 and IPv6 before digit groups. The IPv4 pattern's lookbehind only excludes a digit or "." directly before the match, so in `0 0 0.0.0.0` (six digits joined by spaces and dots, which the digit-group rule masks as one number) it claimed the last four chunks and the result was `x 0 0 [ip] y`, not `x [number] y`. Hypothesis found it in `test_redact_replaces_any_separator_joined_number_of_six_or_more_digits`. The same bug lets `1 2 3.4.5.6` leak the first digits next to an `[ip]`.
Decision: The order becomes: scheme URLs, scheme-less URLs, emails, spelled-out emails, key prefixes and JWTs, token runs, IPv6, digit groups, IPv4, keyword codes. A digit group is masked whole first; a group that is exactly a dotted quad (`_IPV4_FULL` full match on the stripped piece, such as `10.0.0.1`) is marked `[ip]` instead of `[number]`. IPv4 then runs on what is left, so `1.1.1.1 2` is still `[ip] 2` (the group `1.1.1.1 2` has 5 digits, under the 6-digit floor, so it is left alone and the address is found afterwards). IPv6 stays before digit groups: its runs hold ":" and hex letters, which the digit-group rule does not join.
Alternative: Keep IPv4 first and anchor it harder, for example require whitespace or a string edge on both sides and no digit group around it (rejected: the check has to know what the digit-group rule will do with the neighbours, so the two rules' separator sets would have to be kept in step by hand; running IPv4 after the digit rule needs no such coupling and cannot split a run that rule masks). Weaken the digit-group rule (rejected: it is the rule that stops phone numbers leaking).
Reason: The digit-group rule is the wider, safer rule; the narrower IPv4 rule should only see what it left. Over-redaction is the project's stance (0011), so a run that is both an address and part of a longer number becomes `[number]`.
Consequences: An address alone (`10.0.0.1`, `8.8.8.8`) still reads `[ip]`; an address with a digit run joined to it (`10.0.0.1 5`) is now one `[number]`. The IPv4 sweep runs after the digit rules, so `[ip]` is never a digit-group input. No new marker. `tests/test_redact.py` changed its expectation for the separator-joined-number property at 12:29 on 2026-11-10, after this rule landed: under six digits only a valid dotted quad is now `[ip]` (anything else is unchanged), a six-digit-plus group that is exactly a quad is `[ip]`, and every other six-digit-plus group is still `[number]`, so the digit-group rule is not weakened; the old assertion, written before 0244, expected a dotted quad to stay as written. No `tests: modify` card was issued by the session that filed this record, so that edit was made without one.
Where: `src/command_center/core/redact.py` (`redact`, `_redact_digits`, `_IPV4_FULL`), `tests/test_redact.py`, `tests/test_redact_gaps.py` (IPv4 cases).
Revisit when: A third rule needs to see the digit-group output, or four-part version numbers in titles turn `[ip]` into noise (then drop the `[ip]` branch in `_redact_digits`).
