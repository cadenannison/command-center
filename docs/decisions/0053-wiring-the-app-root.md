# 0053. App wiring: summary route always mounted, scheduler started by the lifespan, summary built lazily

Status: accepted

Context: Task 2z wires the five source adapters, the summary service, the web router, static files and a sync loop into the production app. The card says to mount `api/summary_routes.router` "when the container has a summary service", but the production container is built in the lifespan (decision 0021), after the routes are registered, so the app cannot know at construction whether `container.summary` is set.
Decisions:
1. The summary router is always mounted. While `container.summary` is `None` it answers 404 `Summaries are off` (decision 0037), so nothing is sent and no provider exists. `GET /v1/summary` now appears in `docs/generated/openapi.json`; for the mobile repo it is a new path, not a change to an existing one.
2. `api.create_app(container, *, sync_interval_minutes=None)`. When the interval is given, the lifespan starts a `services.scheduler.SyncScheduler` over `container.sync` and stops it on shutdown. Tests that build the app without an interval get no background task. `app.build_app(settings)` passes `Settings.sync_interval_minutes`; `create_app()` and `main()` both use it.
3. The scheduler runs `sync_all` at startup without delaying the server, then every interval. Any exception from a round is logged by class name only and the loop continues; cancellation ends it. There is no scheduled summary job: `SummaryService.get` builds the day's summary on the first request and caches it (decision 0035).
4. Adapters are built with `ZoneInfo(settings.tz)` and `SystemClock` where the constructor asks (apple_calendar and learningsuite take both; canvas, gmail and weather take the clock). Gmail's VIP and muted sender lists have no setting yet, so they keep their empty defaults.
5. `SummaryService` is built only when `summary_enabled`. The provider is `summary_provider` (`gemini` or `ollama`) with `summary_model` when set, else the adapter's own default. The Gemini key is read from `SecretStore` source `gemini`, key `api_key`, on each call (decision 0036).
6. `api/factory.py` imports `web.create_router` to mount the pages, as the card says. `docs/MAP.md` now lists `web` in the api row for that one file; no import-linter contract forbids it, so `mise run arch` is unchanged. `web` does not import `api`.
7. No `gemini` source adapter is registered. The settings page lists registered adapters, so the Gemini card described in `docs/contracts/web.md` does not appear yet and the key has no UI to enter it. Open question for the owner, see the task report; it contradicts the gemini card listed in `docs/contracts/web.md`.
Alternative: (a) Mount the summary router only when a `Container` instance is passed: two behaviours for one app. (b) Start the scheduler from `app.py`: the composition root does not own the lifespan. (b2) Mount the web router and `/static` from `app.py` to keep the api row of MAP unchanged: the Host check and lifespan live in the factory, and tests would have to repeat the mounting. (c) Register a do-nothing `gemini` SourceAdapter so the card appears: it would add a fake source to `sync_all` and the sources list, a design choice that is not this task's.
Reason: Always mounting keeps one shape and keeps the off-by-default test direct. The interval as a `create_app` argument keeps all lifespan work in one place and out of tests.
Where: `src/command_center/app.py`, `api/factory.py`, `services/scheduler.py`; `tests/test_end_to_end.py`, `tests/test_scheduler.py`.
Test edit (allowed by the project manager through `.claude/allow-test-edits`): in `tests/test_app_wiring.py` only the three assertions that assumed no sources were changed, to the exact five names `canvas, apple_calendar, learningsuite, gmail, weather`: `sync.sources()`, the `source` of each `/v1/settings` entry (not the keys or sync state, which come from the real OS keychain and read `error` when an earlier test in the run has left it unavailable) and the `source` of each state `POST /v1/sync` returns. Test function names were left alone, so `..._with_no_sources_registered` and `..._an_empty_agenda_and_settings` are now misleading.
Revisit when: workers take over scheduling (distributed mode); a way to enter the Gemini key is decided; the Gmail sender lists become settings; the shutdown side effects are addressed: a source's in-memory sync state stays `syncing` if the scheduler is stopped mid-sync, and a database write already running on a worker thread finishes after `stop()` returns.
