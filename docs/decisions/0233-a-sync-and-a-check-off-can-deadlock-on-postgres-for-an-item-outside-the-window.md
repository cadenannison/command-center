# 0233. A sync and a check-off can deadlock on Postgres for an item stored outside the sync's window

Status: accepted as a known gap; not fixed. The project manager decided to leave the sync's locking alone: it happens only on Postgres (the optional distributed mode) for an item stored outside the window, a losing sync is redelivered, and changing what every sync locks without a running Postgres test is the bigger risk. Follow-up is a backlog card (retry a check-off once on a deadlock, verified in the CI integration job). Found by the reviewer of 0230; the lock order predates it.

Context: A check-off takes the event row's lock (`read_event(..., lock=True)`) and then inserts the ledger row. `replace_events` locks only the event rows inside its window (`SELECT ... FOR UPDATE`), then `record_sync` inserts ledger rows, and the event rows it writes are touched last (`session.merge`, which takes their lock). For an incoming item that is stored outside the window (a due date moved into it), the sync inserts the ledger row first and takes the event lock second, the opposite order to the check-off: the check-off holds the event row and waits on the sync's uncommitted ledger row, and the sync waits for the event row. Postgres ends one with a deadlock error after `deadlock_timeout`. A sync that loses is redelivered by the normalizer (it retries on anything but `ValueError`); a check-off that loses surfaces as a server error, because `_tolerating_concurrent_writes` catches only `IntegrityError`. Before 0230 the same overlap ended as a key clash instead; 0230 removes that outcome and leaves this one. SQLite cannot deadlock here: the first write takes the whole-database lock.
Decision: Leave the lock order as it is, and say so in `storage.md` and in the comment in `replace_events`. This is a rare overlap (a check-off on a moved item within the milliseconds of that item's sync) and costs one retry or one failed click.
Alternative: Lock the incoming event rows that are outside the window (`SELECT id FROM events WHERE id IN (...) FOR UPDATE`, ordered by id) before `record_sync`, so the sync takes event locks first on every path (recommended if this ever shows up in a log; it adds one locking read per sync and has to be tested on Postgres with two connections); retry a check-off on `DBAPIError` for a deadlock (hides the order problem and needs a failure class and a cap).
Reason: The fix changes what every sync locks and cannot be tested on one thread or on SQLite, so it is not made blind in a data-fix task. The project manager should choose.
Where: `src/command_center/storage/sqlite.py` (`replace_events`), `src/command_center/storage/sqlite_items.py` (`_known_row`), `src/command_center/storage/sqlite_ledger.py` (`insert_or_get`).
Revisit when: A deadlock error from a check-off or a sync is seen on Postgres, or a Postgres two-connection test harness exists.
