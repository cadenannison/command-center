# 0180. City search returns up to five candidates and never picks one

Status: accepted

Context: Task W1 lets the weather form take a city name instead of coordinates. Open-Meteo's forecast API takes only coordinates, so a name has to be resolved first, and a name is ambiguous ("Springfield" is in more than ten US states). The backlog left open whether to take the first match or ask for "City, State".
Decision:
- `GET /v1/geocode?q=` returns a bare JSON list of up to 5 `GeocodeCandidate` (`name`, `region`, `country`, `latitude`, `longitude`, `population`) in Open-Meteo's own order, from `https://geocoding-api.open-meteo.com/v1/search` (`count=5`, `language=en`, 10 s timeout, no redirects). Nothing is picked for the caller: the user chooses, and the stored credentials stay `latitude` and `longitude` (persisted keys, never renamed). No match is `200 []`.
- `q` is trimmed and is 2 to 100 characters (Open-Meteo returns nothing for fewer than 2); a bad `q` is the usual 422 that never echoes the input. Inner whitespace is collapsed before the call.
- The route is loopback only (decision 0182), rate limited by `GeocodeService` to 10 searches per rolling 60 seconds across all callers (429 with `Retry-After`; a search that fails still counts; a refused one does not extend the wait), and its answers are `Cache-Control: no-store`.
- A provider failure is 502 whose `detail` is `City search failed: ` plus the adapter's fixed text, through `safe_message` (redacted, at most 200 characters). An adapter's messages never contain the query. A container built without a geocoder answers 404.
- Layers: `core/geocode.py` (the model, the length bounds, `normalise_query`) and the `Geocoder` Protocol in `core/ports.py`; `adapters/weather_geocode.py` (`OpenMeteoGeocoder`); `services/geocode.py` (`GeocodeService`); `api/geocode_routes.py`; `Container.geocode` (last field, default `None`) built in `app.py`. The adapter reuses `TransientError` and `FatalError`, which are the failure classes the services already map for an adapter.
Alternative: Take the first match and label it (a wrong "Springfield" would be stored silently); require "City, State" (Open-Meteo matches only the exact text after a comma, so a user's spelling of the state would often find nothing); call the geocoder inside the adapter's `validate` and store the resolved pair (the user could not see or correct a wrong match, and `validate` has no list to return); a per-caller limit (every request reaches the api from 127.0.0.1, so there is no caller to tell apart, as with the pairing lock).
Reason: A person must see "Springfield, Illinois" to pick the right one, and a read-only list route leaves the existing connect flow and its stored keys untouched, so the change is additive for the mobile repo.
Where: `src/command_center/core/geocode.py`, `adapters/weather_geocode.py`, `services/geocode.py`, `api/geocode_routes.py`; tests `tests/test_weather_geocode_adapter.py`, `tests/test_geocode_service.py`, `tests/test_geocode_api.py`, `tests/test_app_geocode.py`.
Revisit when: The limit of 10 a minute is too tight for real use, a second location is supported (the form would then hold more than one result), or a caller other than the web form needs the route.
Sources (checked 2026-11-09): https://open-meteo.com/en/docs/geocoding-api gives the endpoint `geocoding-api.open-meteo.com/v1/search`, `name` (required; empty and one-character searches return no results, two characters match an exact name), `count` 1-100 (default 10), `language`, `format`, and result fields `name`, `latitude`, `longitude`, `admin1`, `country`, `population` (empty fields are omitted); invalid parameters are HTTP 400 `{"error": true, "reason": ...}`. The page states no rate limit and credits "Location data based on GeoNames".
