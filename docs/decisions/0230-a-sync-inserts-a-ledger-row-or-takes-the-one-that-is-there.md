# 0230. A sync inserts a ledger row with ON CONFLICT DO NOTHING and re-reads it

Status: accepted. Refines the clash handling of 0128 for the sync side.

Context: `record_sync` read a ledger row with `session.get` and, when there was none, made one with `session.add`. A check-off that commits the same row between that read and the flush made the flush a primary-key clash, which rolled the whole report back (the sink's transaction, so the events and the sync state with it) and left the report to be redelivered. 0128 handled the same clash on the check-off side (it runs again); the sync side had nothing. On Postgres the race needs an item the sync is about to write that is stored outside its window (or whose event the sync's window query does not lock): inside the window the sync's `SELECT ... FOR UPDATE` on the event rows makes a check-off wait, so both orders agree.
Decision: `sqlite_ledger.insert_or_get` runs `INSERT ... ON CONFLICT DO NOTHING` (the Postgres or the SQLite construct, by dialect, like `lock_generation`) and then re-reads the row with `populate_existing`. `_mark_gone` and `_append_source_completion` use it in place of `session.add`. A row that turns out to be a check-off's is used as it is, so the sync's completion entry joins the user's entry. `_mark_gone` checks for a completion after it has the row, so an item a check-off completed first is not called gone. If the row is deleted between the insert and the re-read (a disconnect committing in that gap) `insert_or_get` raises `LedgerRowVanishedError`; the report fails and is redelivered, and the redelivery finds no ledger row to clash with.
Alternative: Catch `IntegrityError` and run `record_sync` again (a rolled-back transaction after a clash on Postgres cannot continue, so the whole replace would have to restart); a savepoint around each insert (works, but one per new row on the hot path of every sync); `SELECT ... FOR UPDATE` on a missing row (locks nothing).
Reason: One statement that cannot clash, one re-read, no retry loop, and the same shape on both databases.
Where: `src/command_center/storage/sqlite_ledger.py` (`insert_or_get`, `_mark_gone`, `_append_source_completion`); `tests/test_ledger_races.py` (the done case on SQLite and, with `CC_TEST_POSTGRES_URL`, Postgres; the gone case on SQLite only, because on Postgres the window lock keeps the check-off out). The Postgres variant has not been run in this session (no server).
Known gap: on Postgres the sync inserts the ledger row before it rewrites the event row, while a check-off locks the event row before it inserts the ledger row, so for an item stored outside the sync's window the two can deadlock; see 0233.
Revisit when: A completion insert (`add_completion`) can race on the same key (two writers of one `source` entry; today the generation lock serializes syncs), or the ledger gets a second writer.
