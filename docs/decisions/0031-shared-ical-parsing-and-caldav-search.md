# 0031. Shared iCal parsing module; `search` instead of `date_search`; expansion library

Status: accepted

Context: Task 2b names two files, `caldav_apple.py` and `ical_feed.py`, and says to use `date_search(expand=True)`. Both adapters must turn iCalendar text into the same tz-aware Events, with the same window rule (`adapters.md` rule 10).
Decision:
1. The parsing lives in a third file, `adapters/ical_events.py` (pure functions; imports `icalendar` and `recurring_ical_events`, no vendor-restricted SDK). Both adapters call it, so a CalDAV result and a feed result are expanded, localised, window-filtered and id'd identically. Ids hash `source`, a scope (the calendar URL for CalDAV, the feed number for feeds), the UID and the start instant, so the same UID in two calendars stays two events.
2. CalDAV uses `Calendar.search(start=, end=, event=True, expand=True)`, which is what caldav 3.7 documents `date_search` as migrating to (it is deprecated and removed in caldav 4.0). Same request and expansion.
3. Recurrence is expanded with `recurring_ical_events`, for feeds and again on CalDAV results (idempotent for already-expanded instances, and it expands a master the server left whole). It is not listed in `pyproject.toml`; it is locked in `uv.lock` and is a hard requirement of `caldav` and `icalendar-searcher`. AGENTS.md forbids editing `pyproject.toml`, so the human decides whether to declare it directly.
4. Constructors are `(tz, clock, ...)`: the `Clock` supplies `fetched_at`; `AppleCalendarAdapter` also takes a `session_factory` seam (default: the real iCloud login) so tests use a fake, `IcalFeedAdapter` needs none because respx fakes httpx.
5. CalDAV is asked for the window padded by 2 days on each side (`ical_events.EXPANSION_PAD`) and `events_in_window` filters exactly. caldav matches floating and all-day items in the zone of the request, which in production is UTC (`horizon_window`), while we place them in the adapter's tz; an unpadded request misses edge items and `replace` would then delete them. Any other exception from the session (a parser or lookup error inside caldav) becomes `TransientError` carrying only its class name, unchained.
6. Smaller choices: a CANCELLED item is skipped; an item without DTSTART is dropped before expansion (the library raises on it and it can match no window); feeds are fetched one after another so the lowest failing feed number is reported and later feeds are not requested; 401/403 -> `AuthExpired`, 404/410 and any 3xx -> `FatalError`, 408/425/429/5xx and network errors -> `TransientError`; `validate` returns `ok=False` naming the feed for `AuthExpired`/`FatalError` (the connect flow drops an `AuthExpired` message) and lets `TransientError` propagate.
Alternative: put the parsing in `ical_feed.py` and import it from `caldav_apple.py` (couples two adapters); keep `date_search` (emits a DeprecationWarning, gone in 4.0); write the recurrence expansion by hand on `dateutil` (DST, EXDATE and RECURRENCE-ID are easy to get wrong).
Why: One tested place for the rules that must match across sources, and no hand-rolled calendar maths.
Where: `src/command_center/adapters/ical_events.py`, `caldav_apple.py`, `ical_feed.py`; tests `test_ical_events.py`, `test_caldav_apple.py`, `test_ical_feed.py`.
Revisit when: caldav 4.0 changes `search`; `recurring_ical_events` is declared in `pyproject.toml` (then drop point 3's caveat); a third iCal source appears; feed counts grow enough to want concurrent fetching.
