# 0113. The Today summary card has five states, and `generate` fails loudly

Status: accepted (point 4 and Alternative (a) superseded by 0116)

Context: Task A2 wants the Today page to always show a summary card: not enabled (what is sent, with an Enable button), no key, generating, a result with Regenerate, and a redacted error. Until now the page showed nothing while off, and `SummaryService.get` swallowed provider failures into a stored or template summary, so a failure was invisible.
Decision: (1) `web/summary.py` builds a `SummaryCard` (`off`, `no_key`, `generating`, `ready`, `error`) and the routes `POST /summary/settings` (form `enabled` on or off, `provider`) and `POST /summary/generate?date=&refresh=` return the `_summary.html` fragment that replaces `#summary-card` (HTMX outerHTML). They live in `web/summary.py` and are mounted in `web/router.py`; `web/settings_routes.py` and `services/settings.py` are untouched. (2) `SummaryService.generate(day, refresh=False)` is the loud variant: a stored summary is returned unless `refresh`; a provider failure raises `SummaryUnavailableError(reason)` with `reason` `failed` or `rate_limited`, with no fallback to an earlier day or the template. `get` and `/v1/summary` are unchanged. (3) The card shows fixed messages chosen by `reason`; any other exception shows the same generic message and only its class name is logged. Provider text never reaches the page. (4) A page load generates in the request, as before, so a slow provider still delays the page. The `generating` state is served after Enable or a provider change: the response comes back at once and its `hx-trigger="load"` posts to `/summary/generate`. Regenerate shows an in-flight "Generating…" beside the disabled button. (5) `no_key` is decided from `container.settings.status()`: a registered `gemini` entry with no `api_key` set. An unregistered entry counts as having a key. The card links to `/settings#source-gemini`. (6) With no control (a container built without one) the card still renders but has no Enable button, and `/summary/settings` answers 404. (7) Test edit allowed by the project manager: `tests/test_end_to_end.py::test_the_page_has_no_summary_block_while_summaries_are_off` became `test_the_page_shows_the_not_enabled_summary_card_while_summaries_are_off`, expecting the not-enabled card. `tests/test_web_pages.py::test_today_has_no_summary_block_without_a_summary_service` still asserts the old behaviour (no `summary-h` section) and was not edited; it fails until the project manager rules on it.
Alternative: (a) Generate the first summary asynchronously on every page load: faster page, but existing tests expect the text in the first response and a failure test expects the error in it. (b) Make `get` raise: changes the documented `/v1/summary` behaviour the mobile repo relies on. (c) Show the provider's error text: it can carry request details. (d) Read the key through the secret store from the web: the web imports services only.
Reason: The states are explicit and testable, the opt-in text is shown before anything is sent, and a failure is visible without leaking.
Where: `web/summary.py`, `web/templates/_summary.html`, `web/templates/today.html`, `web/router.py`, `web/pages.py`, `services/summary.py`, `services/errors.py`; `tests/test_web_summary_card.py`, `tests/test_summary_generate.py`, `tests/test_end_to_end.py`.
Revisit when: provider calls get slow enough that the page load should not wait (move the first generation to the `generating` state), or `SettingsService` offers a cheaper key-status call than `status()`, which reads every source.
