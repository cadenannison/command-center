# 0190. The Gmail card explains itself from per-source form fields and shows the not-connected panel only before anything is stored

Status: accepted

Context: Card G1 asked for the Gmail card's pending-connect wording to tell a first-time user what is happening, what to do next, how long it takes and what success looks like. The old card said only "Not connected", an "OAuth client JSON" label and, while connecting, "Waiting for Google sign-in…". Gmail is the one source whose connect needs a one-time Google Cloud setup and then a browser sign-in, so it needs more words than the others.
Decision: The copy lives in `web/sources.py` as new optional `SourceForm` fields: `note` (always shown: read-only, only to find replies you owe, "stored only on this computer, never in the project folder or any file you commit", never shown again after saving; it does not name the keychain because the Docker file-store mode keeps secrets in a file, a correction made on the project manager's instruction after the first draft said "keychain"), `waiting` (the busy line during connect), `pending` (a `PendingHelp` with now, steps, time and result) and `syncing_note` (shown while any sync runs, worded "Checking your recent mail now; this takes under a minute." so it is true for a scheduled sync as well as the one after Connect; a first draft said "Signed in", which a reviewer found false on a scheduled sync). `card_view` passes `pending` only when the status is `none` (nothing stored, no sync recorded) and `syncing_note` only while the status is `syncing`; `_card.html` draws them. The status poll (`_status_fragment.html`) also swaps the note's slot out of band (`_syncing_note.html`), so it appears when a sync starts and is emptied and hidden when the sync ends; a source without a note has no slot. A source that sets none of them looks exactly as before. The detailed steps stay in the existing collapsible `<details class="howto">`.
Alternative: Hard-code the Gmail text in `_card.html` behind `card.source == "gmail"` (rejected: the template would know a vendor by name and the next source needing a first-run explanation would copy it). Put the plain steps into `howto.py` only (rejected: it is collapsed by default, so the first-time user would not see what is happening or what to do next).
Reason: Per-source text already comes from `sources.py` (the Gemini caveat is a `note`), so the card stays one template and the words stay with the source's other labels. Tying the panel to status `none` means it disappears the moment something is stored, so it never describes a state the user has left.
Consequences: A failed first connect still shows the panel (nothing was stored, so the status stays `none`) with the failure line under the buttons. The Reconnect state has no new copy; it was out of the card's scope. The card makes the claim "does not read message bodies"; it holds because `adapters/gmail.py` requests `format="metadata"`.
Where: `src/command_center/web/sources.py` (`PendingHelp`, `GMAIL_*`), `src/command_center/web/cards.py`, `src/command_center/web/templates/_card.html`, `docs/contracts/web.md`; `tests/test_web_gmail_card.py`.
Revisit when: Another source needs a first-run explanation (consider a shared structure), the Reconnect state is reworded, or the UI redesign replaces the card layout.
