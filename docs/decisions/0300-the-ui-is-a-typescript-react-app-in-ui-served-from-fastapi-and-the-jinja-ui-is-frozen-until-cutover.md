# 0300. The UI is a TypeScript React app in ui/, served from FastAPI; the Jinja UI is frozen until cutover

Status: accepted

Context: The Jinja2 + HTMX UI (decision 0008) is the only front end. The redesign needs richer widgets, a typed client for the /v1 API and browser-level accessibility tests, and the later Mac, iPhone, Windows and Android clients (decision 0304) should share one language and one API contract. Decision 0008 chose "one-language stack, no JS build chain"; this record changes that for the UI only.
Decision: The new UI is a single-page app in `ui/` in this repo.
- Stack: Vite, React and TypeScript (strict); Tailwind CSS with shadcn/ui components (Radix primitives, copied into `ui/`); TanStack Query for server state and TanStack Router for routes; pnpm as the package manager; Vitest for unit and component tests; Playwright with axe-core for browser and accessibility tests.
- Where it is served: the built files are served same-origin from the FastAPI process, on 127.0.0.1 like the rest (AGENTS.md rule 5). No second server, no CORS, no cross-origin token handling. A dev server is for development only (decision 0301 restricts its hosts).
- Typed client: generated from `docs/generated/openapi.json` into `ui/src/api/generated/`, which is never hand-edited (the same rule as `docs/generated/`). A route or schema change reaches the UI by `gen:build` followed by regenerating the client, so the API stays the single contract.
- The Jinja UI is frozen: bug fixes and security fixes only, no new pages or widgets, until the cutover. The cutover is a separate task and a new record that supersedes the Jinja parts of 0008 and removes `src/command_center/web`.
- The Python architecture rules do not change. `ui/` is outside `src/command_center` and never imports Python; it reaches the app only through /v1 (decision 0302). The macOS menu-bar launcher (rumps) stays as decision 0008 left it.
Alternative: Keep growing Jinja + HTMX (rejected: rich interactive widgets and a shared client for the later platforms are awkward in server-rendered fragments, and there is no browser-level accessibility test). Next.js or another server-rendering framework (rejected: it adds a second server process and a Node runtime in production; a static build served by FastAPI needs neither). A separate repo for the UI (rejected: the openapi.json contract and the UI change together, and one gate should see both). Hand-written API types (rejected: they drift from the contract). npm or yarn instead of pnpm (rejected: pnpm's blocked-by-default install scripts and release-age setting are what decision 0301 builds on).
Reason: One repo and one origin keep the security model of a local-first app unchanged: no CORS, no tokens in browsers beyond what the API already uses, one place that gates both languages. A generated client turns every API change into a type error in the UI.
Consequences: The repo now has two languages and two dependency trees. Each gets its own gates (`mise run ui:check`, decision 0303) and its own supply-chain rules (0301). Two UIs exist side by side until cutover, so a bug fix in a Jinja page is not ported automatically. A Node toolchain is needed to build the UI; running the Python app after cutover needs only the built files.
Where: `ui/` and `ui/src/api/generated/` (to be created by a later task, not by K1), `docs/decisions/0008-ui.md` (Jinja2 + HTMX decision this narrows), `docs/generated/openapi.json` (client source).
Revisit when: The cutover task starts (supersede the Jinja parts of 0008), or the typed-client generator, router or component library is replaced.
