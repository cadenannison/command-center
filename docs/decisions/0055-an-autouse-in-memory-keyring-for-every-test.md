# 0055. An autouse in-memory keyring for every test

Status: accepted

Context: `app.build_container` builds `KeyringSecretStore`, so the wiring tests (`tests/test_app_wiring.py`, `tests/test_app_sources_and_summary.py`) read the developer's real OS keychain. What `GET /v1/settings` and `POST /v1/sync` returned depended on what earlier runs had left there, and on whether the keychain was locked (decision 0053 recorded this: the 2z task narrowed those assertions to source names for that reason). `.claude/rules/tests.md` already forbids a real keychain in tests.
Decision: `tests/conftest.py` has an autouse fixture, `keyring_backend`, that installs a fresh `InMemoryKeyring` with `keyring.set_keyring` for every test and puts the previous backend back afterwards, also when the test fails. The backend and the `in_memory_keyring()` context manager it uses live in `tests/keyring_support.py`. `tests/test_hermetic_keyring.py` pins the behaviour: the active backend is the in-memory one, the secret store writes only to it, each test starts empty, and the previous backend is restored on exit and when the body raises. `adapters/keyring_store.py` and `app.py` are unchanged. `tests/test_keyring_store.py` keeps its own autouse fake; it runs after the conftest one, so it wins for those tests and restores correctly.
Alternative: (a) A fixture only the wiring tests ask for: a new test that builds the container and forgets the fixture reads the real keychain again, and opting in means editing existing tests. (b) Let `build_container` take a `SecretStore` argument and pass a fake: it changes the composition root's signature for a test's sake, and the wiring test would then no longer exercise the real `KeyringSecretStore`. (c) Monkeypatch `KeyringSecretStore` in the tests: the real store, including its blob format and error mapping, would not be what the wiring test runs.
Reason: Setting the backend at the keyring boundary keeps the real store, the real container and the real services in the test, and the autouse scope makes hermeticity the default, not something to remember. `set_keyring` is process-global, but pytest runs tests of one process one at a time and the fixture restores in `finally`, so random order cannot leak a backend from one test to the next.
Where: `tests/conftest.py`, `tests/keyring_support.py`, `tests/test_hermetic_keyring.py`.
Revisit when: tests run in parallel inside one process (threads, not xdist processes), which would make the process-global backend shared; or `build_container` takes its infrastructure as arguments.
