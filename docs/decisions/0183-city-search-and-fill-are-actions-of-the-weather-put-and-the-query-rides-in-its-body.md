# 0183. City search and fill are two more actions of PUT /settings/weather, and the typed city rides in the body

Status: accepted

Context: Task W1-web puts a "Find a city" box on the weather card. The `GET /v1/geocode` route (0180) is loopback-only and takes the text in a query string, which uvicorn's access log prints (0181). The web form needs a search, and picking a result has to fill the two editable inputs without storing anything. Every route must be classified in `tests/test_remote_policy.py`, so a new route would force an edit to that existing test.
Decision:
- `PUT /settings/weather` takes two more `action` values (0102): `search` (field `city`; up to five candidates, none picked, nothing stored) and `fill` (fields `latitude`, `longitude`, `label`; answers with the two inputs as `hx-swap-oob` replacements plus "Nothing is saved until you press Connect"; nothing stored). `connect` stays the default, so Connect is the only action that stores. Another source answers either action with 422. No new route, so `/v1` and `openapi.json` are unchanged.
- The search form is its own `<form>` before the credentials form, with an `hx-put` and no `hx-get`: the typed text travels in the request body, never in a URL, so the uvicorn access line is `PUT /settings/weather` and `QUIET_QUERY_PATHS` (the note in 0181) needs no entry. The input is named `city`; `read_credentials` only reads a source's own fields, so a `city` sent with Connect is ignored and never stored.
- The web layer calls `services.geocode` only (no adapter). `CitySearch` in `web/city_search.py` shows five states as fixed text: no match, query shorter than 2 or longer than 100 characters (not sent), rate limited (with the wait), failure (the service's redacted `City search failed: ...`), and no geocoder (`Container.geocode is None`). No answer repeats the query.
- `fill` is a server round trip, not JavaScript: the Use button sends the coordinates the page already holds, the server checks they are finite and in range (latitude within 90, longitude within 180), and returns the inputs rendered by the same macro as the card (`_field.html`), so the replacements cannot drift from the originals. The `label` the button sends is shown escaped and cut to 120 characters.
Alternative: A new `POST /settings/weather/search` route (needs a row in the phone-policy table, an existing test) or `GET /settings/weather/search?q=` (puts the text in the access log until `QUIET_QUERY_PATHS` grows); `hx-on:click` that copies the coordinates in the browser (needs htmx eval, cannot be tested here); an unnamed input read by a `js:` `hx-vals`; searching with the geocoder inside Connect (the user could not see or correct a wrong match; 0180).
Reason: The PUT route already carries the card's actions, is already phone-denied and CSRF-checked, and keeps the text out of every URL. A server fill is testable with the fake geocoder and keeps "never auto-pick" and "nothing stored until Connect" checkable in one place.
Where: `src/command_center/web/city_search.py`, `web/settings_actions.py` (dispatch, `NO_CITY_SEARCH`), `web/sources.py` (`SourceForm.city_search`), `web/cards.py` (`CardView.city_search`), templates `_city_search.html`, `_city_results.html`, `_field.html`; tests `tests/test_web_city_search.py`. `tests/test_web_settings.py::test_cards_only_ask_for_their_own_fields` expects the weather card's named inputs to be `city`, `latitude`, `longitude`; the project manager approved that one edit, and the guard hook blocked it until `.claude/allow-test-edits` exists.
Revisit when: A second source needs a lookup box (`city_search` becomes a general "lookup" flag), the htmx round trip for Use feels slow, or a phone needs to search.
Sources (checked 2026-11-09): decisions 0102, 0180, 0181; https://htmx.org/attributes/hx-swap-oob/ semantics are used as in `_action_result.html` (an element with `hx-swap-oob="true"` replaces the page element with the same id).
